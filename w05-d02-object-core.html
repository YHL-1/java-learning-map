01 / OBJECT

所有类的祖宗：Object

Java 里每个类都隐式继承 Object。它定义了 11 个方法，其中真正需要你关心的只有 3 个：equals、hashCode、toString。

方法作用要不要重写
equals(Object)判断「逻辑相等」值对象必须重写
hashCode()返回散列值，供 HashMap/HashSet 定位重写 equals 就必须重写
toString()默认输出 类名@十六进制hash建议重写，日志友好
getClass()返回运行时 Class 对象（final）不可重写
clone()浅拷贝（protected）不推荐，优先用拷贝构造器
finalize()GC 前回调已废弃，别用
wait / notify / notifyAll线程通信（final）不重写

默认 equals 到底比较了什么？

Object.equals 的实现就是 return this == obj;——比较地址。
所以两个内容完全一样的对象，不重写 equals 就永远不相等。这也是为什么 new String("a").equals(new String("a")) 为 true 而 == 为 false：String 重写了 equals。

三个概念先分清

==比较值。基本类型比值本身；引用类型比地址（是不是同一个对象）。
equals方法，默认同 ==；重写后可定义为「内容相等」。
hashCode方法，返回 int 散列值。只被哈希容器（HashMap/HashSet/HashTable）使用。

02 / EQUALS

equals 的五条契约

重写 equals 不是"想怎么写就怎么写"，它必须满足数学上的等价关系。破坏任何一条，集合、去重、缓存都会出现难以复现的 bug。

自反性x.equals(x) 必须为 true
对称性x.equals(y) 为 true，则 y.equals(x) 也必须为 true
传递性x=y 且 y=z，则 x=z
一致性只要对象状态没变，多次调用结果必须一致（所以别用随机数、时间戳参与比较）
非空性x.equals(null) 必须返回 false，不能抛异常

标准写法（照抄这段）

@Override
public boolean equals(Object o) {
    if (this == o) return true;                    // ① 同一引用，快速返回
    if (o == null || getClass() != o.getClass()) return false; // ② 类型必须完全一致
    Order other = (Order) o;
    return id == other.id
        && Objects.equals(name, other.name)              // ③ 引用字段用 Objects.equals
        && amount.compareTo(other.amount) == 0;             // ④ BigDecimal 用 compareTo
}
@Override
public int hashCode() { return Objects.hash(id, name, amount); }

为什么用 getClass() 而不是 instanceof？

用 instanceof 时，子类实例和父类实例可能互相 equals，但方向不同结果不同，破坏对称性。
典型场景：Dog extends Animal，规则写不好就出现 a.equals(d)==true 但 d.equals(a)==false。
选择：值对象用 getClass() 严格判等；需要对子类开放时才用 instanceof，并且要在父类里加 final 或写明契约。

实体 vs 值对象：判等依据不同

实体 Entity值对象 Value Object
标志有唯一 id，状态会变无 id，不可变
判等依据只用 id所有字段
例子User、Order、ProductMoney、Address、DateRange、UserId
hashCode基于 id基于全部字段

这条区分很关键：订单的金额从 100 改成 200，它还是同一个订单（id 相同）；但 100 元和 200 元是两个不同的值对象。

所以 hashCode 的约定是

05 / STRING

String：不可变与常量池

String 是 Java 里最特殊的类。它的"不可变"不是为了性能，而是为了安全、共享和缓存。搞懂它，== 和 equals 的经典题就一次性解决了。

不可变是怎么做到的

public final class String implements Serializable, Comparable<String> {
    private final byte[] value;   // Java 9+ 用 byte[] + coder，Latin1/UTF16 省内存
    private final byte coder;     // 0 = Latin1, 1 = UTF16
    private int hash;              // 懒计算并缓存 hashCode
}
  • class final：不能被继承，防止子类改行为。
  • 字段 final + private：引用不可变，且没有 setter。
  • 没有暴露内部数组：构造时拷贝，取用时也不返回原数组。
  • 所有"修改"方法返回新对象：toUpperCase()、substring()、concat() 都是 new。

不可变带来的四个好处

  • 线程安全：不用加锁，天然可共享
  • hash 可缓存：算一次存起来，适合做 Map key
  • 常量池共享：相同字面量只存一份，省内存
  • 安全：传参给方法不用担心被改，SQL/路径拼接不被注入篡改

代价

每次修改都产生新对象。所以循环里 s += x 会创建大量临时对象——这就是为什么要用 StringBuilder。

自动拆箱的两个陷阱

① null 拆箱直接 NPE

Integer n = null;
int x = n;   // NullPointerException

接口返回 Integer 字段、数据库可空列、Map 取值，都可能拿到 null。拆箱前先判空。

② 三元表达式类型提升

07 / BIGDECIMAL

BigDecimal：钱的计算

D1 讲了"金额必须用 BigDecimal"，D2 要把它彻底用对。核心就三个概念：精度（scale）、舍入模式、比较方式。

先看 double 为什么不行

System.out.println(0.1 + 0.2);          // 0.30000000000000004
System.out.println(1.0 - 0.9);          // 0.09999999999999998
System.out.println(0.1 * 3 == 0.3);       // false

二进制浮点无法精确表示 0.1（就像十进制写不出 1/3）。金额场景差一分钱就是 bug，所以必须用十进制精确表示的 BigDecimal。

第一个坑：不要用 double 构造 BigDecimal

new BigDecimal(0.1);            // 0.1000000000000000055511151231257827...
new BigDecimal("0.1");          // 0.1  ← 正确
BigDecimal.valueOf(0.1);         // 0.1  ← 也正确（内部转 String）

equals 和 compareTo 不是一回事

① 两个"看起来一样"的金额

1.0
unscaled=10, scale=1
1.00
unscaled=100, scale=2

BigDecimal = 未缩放整数 × 10-scale。两者数值相等，但 scale 不同。

② equals 连 scale 一起比

1.0
equals → false
1.00
scale 不同即不相等

这就是「BigDecimal 不能用 equals 比较」的真正原因——不是精度问题，是 scale 参与比较。

③ compareTo 只比数值

1.0
compareTo → 0
1.00
相等

规则：判断金额大小一律用 compareTo == 0。

④ 但放进 HashSet 又会出错

Set<BigDecimal> set = new HashSet<>();
set.add(new BigDecimal("1.0"));
set.add(new BigDecimal("1.00"));
System.out.println(set.size());   // 2 ← 因为 hashCode 也不同

解法：入库前统一 setScale(2, RoundingMode.HALF_UP)，让所有金额的 scale 恒等于 2。这也是 Money 值对象存在的意义。

除法必须指定精度和舍入

BigDecimal a = new BigDecimal("10");
BigDecimal b = new BigDecimal("3");
a.divide(b);                                              // ArithmeticException: Non-terminating decimal
a.divide(b, 2, RoundingMode.HALF_UP);                      // 3.33 ← 正确
a.divide(b, new MathContext(4, RoundingMode.HALF_UP));   // 3.333 ← 按有效数字

八种舍入模式，只需记住 3 个

HALF_UP四舍五入（最常用，和人的直觉一致）
HALF_EVEN银行家舍入（.5 向偶数靠），金融统计常用，避免系统性偏差
DOWN / UP直接截断 / 直接进位，分别用于"不能多收"和"不能少收"的场景

还有两个静态方法的坑

  • toString() 可能输出科学计数法（1E+2），要给人看用 toPlainString()。
  • stripTrailingZeros() 会把 1.00 变成 1，但 scale 可能变成负数（如 1000 → 1E+3），之后 setScale 会报错。谨慎使用。

08 / VALUE OBJECT

任务 2：写一个 Money 值对象

把今天所有知识点收进一个类里：不可变、自校验、统一 scale、正确的 equals/hashCode、安全的运算。

public final class Money implements Comparable<Money> {

    public static final Money ZERO = new Money(BigDecimal.ZERO);
    private static final int SCALE = 2;   // 全局统一两位小数

    private final BigDecimal amount;

    private Money(BigDecimal amount) { this.amount = amount; }

    // 工厂方法：唯一入口，所有校验和规整都在这里
    public static Money of(String yuan) {
        if (yuan == null || yuan.isBlank()) throw new IllegalArgumentException("金额不能为空");
        return of(new BigDecimal(yuan));   // 用 String 构造，避免 double 误差
    }

    public static Money of(BigDecimal v) {
        if (v == null) throw new IllegalArgumentException("金额不能为 null");
        if (v.signum() < 0) throw new IllegalArgumentException("金额不能为负");
        return new Money(v.setScale(SCALE, RoundingMode.HALF_UP));  // 统一 scale
    }

    public Money plus(Money o)  { return new Money(amount.add(o.amount)); }      // 不可变：返回新对象
    public Money minus(Money o) { return of(amount.subtract(o.amount)); }
    public Money times(int n)     { return new Money(amount.multiply(BigDecimal.valueOf(n))); }

    public boolean isGreaterThan(Money o) { return amount.compareTo(o.amount) > 0; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        return amount.compareTo(((Money) o).amount) == 0;   // 用 compareTo，不用 equals
    }
    @Override public int hashCode() { return amount.stripTrailingZeros().hashCode(); }

    @Override public int compareTo(Money o) { return amount.compareTo(o.amount); }
    @Override public String toString() { return amount.toPlainString() + " 元"; }
}

① 唯一入口　Money.of("399.005") → 构造器私有，外部只能走工厂 → 所有 Money 都是合法且 scale=2 的。

② 自动规整　"399.005" → 399.01（HALF_UP）。不会出现 399.005 这种没法入账的值。

③ 运算返回新对象　a.plus(b) 不修改 a 和 b，天然线程安全，可以放心当 Map key。

④ 判等用 compareTo　Money.of("1.0").equals(Money.of("1.00")) → true，因为两边 scale 都被规整成 2。

⑤ 防御性拷贝　BigDecimal 本身不可变，所以不用拷贝；但如果字段是 List 或 Date，getter 要返回副本，否则外部能改内部状态。

record 能替代吗？

public record Money(BigDecimal amount) { }

record 自动生成 equals/hashCode/toString 和全参构造器，字段天然 final。但它的 equals 用的是字段的 equals——对 BigDecimal 来说就是比 scale，所以 1.0 和 1.00 不相等。

结论

简单值对象（UserId、OrderNo）用 record 很爽；但涉及 BigDecimal 的值对象，要手写 equals/hashCode，或者像上面的 Money 一样在构造时把 scale 规整掉——规整之后 record 也能正确工作。

record 的一个坑

如果 record 的字段是可变对象（数组、List、Date），record 的 equals 仍会按引用比较，而且外部能通过 getter 拿到内部集合。record 不等于深度不可变，需要在紧凑构造器里做防御性拷贝。

09 / SELF CHECK

今天的自测

先自己答，再展开。这一天的题面试出现频率极高，值得背到能脱口而出。

== 和 equals 的区别？

== 比较值：基本类型比值，引用类型比地址。equals 是方法，Object 默认实现等同于 ==，重写后一般表示"内容相等"。String、包装类都重写了 equals。

equals 的五条契约？

自反、对称、传递、一致、非空（x.equals(null) 返回 false）。破坏对称性最常见，原因是错误地用了 instanceof 却没处理好子类。

为什么重写 equals 必须重写 hashCode？

HashMap 先按 hashCode 定位桶，再在桶内用 equals 比较。hashCode 不同会落到不同的桶，equals 根本没机会执行，导致"相等的对象存进去却取不出来/去重失败"。

hashCode 相同，equals 一定相同吗？

不一定。hashCode 相同只是"哈希冲突"，还需要 equals 判定。反过来 equals 相同则 hashCode 必须相同。

用可变对象当 HashMap 的 key 会怎样？

插入后如果修改了参与 hashCode 计算的字段，哈希值变化，下次 get 会去错误的桶里找，返回 null，且原 entry 永远无法被正常删除，造成内存泄漏。

new String("abc") 创建了几个对象？

常量池没有 "abc" 时 2 个（池中字面量 + 堆对象）；已有则 1 个（只有堆对象）。

为什么 String 要设计成不可变？

① 线程安全，可自由共享；② hashCode 可缓存，适合做 Map key；③ 常量池才能安全复用同一份对象；④ 安全性，传参和拼接结果不会被篡改。代价是每次修改都产生新对象。

s1 = "abc"、s2 = new String("abc")，s1 == s2 是什么？

false。s1 指向常量池对象，s2 指向堆里新建的对象。s1.equals(s2) 为 true，s2.intern() == s1 为 true。

为什么 Integer a=100,b=100 时 a==b 为 true，1000 时却为 false？

自动装箱调用 Integer.valueOf，-128~127 有 IntegerCache 缓存，返回同一个对象；超出范围每次 new，地址不同。比较包装类一律用 equals。

自动拆箱有哪些坑？

① 包装类为 null 时拆箱抛 NPE；② 三元表达式中若一侧是基本类型，另一侧的包装类会被强制拆箱，null 就炸。参见 flag ? nullableInteger : 0。

BigDecimal 的 equals 和 compareTo 有什么区别？

equals 同时比较数值和 scale（1.0 与 1.00 不相等）；compareTo 只比较数值（相等返回 0）。判断金额是否相等用 compareTo == 0，但要注意 HashSet/HashMap 仍按 equals/hashCode 判断。

为什么不能 new BigDecimal(0.1)？

double 本身就无法精确表示 0.1，构造器会把那个近似值完整带进来，得到 0.1000000000000000055...。应使用 new BigDecimal("0.1") 或 BigDecimal.valueOf(0.1)。

BigDecimal 做除法要注意什么？

必须指定 scale 和 RoundingMode，否则遇到除不尽（如 10/3）会抛 ArithmeticException。

实体和值对象的 equals 分别怎么写？

实体按唯一 id 判等；值对象按全部字段判等，且应设计成不可变（字段 final、无 setter、运算返回新对象）。
