01 / GENERICS

泛型解决的是什么问题

一句话：把类型检查从运行期提前到编译期。没有泛型时，集合里什么都放得进去，取出来还得强转，出错只能等到运行时。

没有泛型（Java 5 之前）
List list = new ArrayList();
list.add("abc");
list.add(123);        // 编译通过，但埋雷

String s = (String) list.get(1);
// 运行时：ClassCastException
有泛型
List<String> list = new ArrayList<>();
list.add("abc");
list.add(123);        // 编译直接报错

String s = list.get(0);  // 不用强转

三种泛型

// ① 泛型类
public class Box<T> {
    private T value;
    public void set(T v) { this.value = v; }
    public T get() { return value; }
}

// ② 泛型接口
public interface Converter<S, R> { R convert(S s); }

// ③ 泛型方法（类型参数写在返回值前面）
public static <T> T first(List<T> list) {
    return list.get(0);
}

// ④ 上界：T 必须是 Comparable 的实现
public static <T extends Comparable<T>> T max(List<T> list) { ... }

四种写法别看混

<T>声明一个类型参数（只有声明处能写）
List<T>使用类型参数
List<String>使用具体类型（参数化类型）
List<?>使用通配符（未知类型）

02 / TYPE ERASURE

类型擦除：泛型是编译期的幻觉

这是 Java 泛型最核心也最反直觉的一点：泛型信息在编译后就没了。`List<String>` 和 `List<Integer>` 在运行时是同一个类。

① 你写的代码

List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
class Box<T> { T value; }

② 编译器擦掉尖括号里的东西

List<String>
→
List
Box<T>
→
Box

类型参数 T 被替换成它的上界：没有上界就是 Object，有 <T extends Number> 就替换成 Number。

③ 字节码里只剩 Object

// Box 编译后实际长这样
class Box {
    Object value;          // T 被擦成 Object
    Object get() { return value; }

    // 编译器在调用处自动插入强转：
    // String s = (String) box.get();
}
// 但编译器会额外记录签名信息（Signature 属性），供反射和调试使用

④ 证据：运行时它们是同一个 Class

System.out.println(a.getClass() == b.getClass());   // true
System.out.println(a.getClass().getName());         // java.util.ArrayList

所以泛型不是"运行时的类型"，只是"编译期的约束"。这就是"泛型擦除"。

擦除带来的五个限制

想做的事能不能原因 / 替代方案
new T()不能运行时不知道 T 是啥。需要传 Class<T> 或 Supplier
new T[10]不能数组需要具体类型。用 (T[]) new Object[10]（不安全）或 Array.newInstance(clazz, n)
x instanceof T不能擦除后没有 T。用 clazz.isInstance(x)
T.class不能同上，需显式传 Class 对象
静态成员用 T不能静态成员属于类本身，与实例的类型参数无关

最容易踩的一个：重载冲突

void f(List<String> list) { }
void f(List<Integer> list) { }
// 编译报错：name clash —— 擦除后两个都是 f(List)

但改成不同的原始类型就可以：f(List<String>) 和 f(Set<String>) 不冲突。

桥接方法：擦除后多态怎么办

class Parent<T> { T get() { return null; } }
class Child extends Parent<String> {
    @Override String get() { return "hi"; }
}
// 擦除后父类方法是 Object get()，子类是 String get() —— 签名不一样，谈何重写？
// 编译器自动生成桥方法：
// Object get() { return get(); }   ← 内部调用真实的 String get()

这就是为什么用反射 getMethods() 时会看到两个 get()，其中一个是 isBridge() 为 true 的合成方法。

为什么 Java 要设计成擦除？

向后兼容。Java 5 引入泛型时，已经有海量运行在旧 JVM 上的代码和非泛型类库。擦除保证了 List<String> 编译出的字节码能在没有泛型支持的旧虚拟机上跑，也能和旧的 List API 二进制兼容。
C# 选择了"具体化泛型"（运行时保留类型信息），代价是必须改 CLR。这是两种取舍。

03 / WILDCARD

PECS：Producer Extends, Consumer Super

通配符只有三个符号，但用错方向的后果是编译不过。记住一句话：extends 只能读，super 只能写。

List<? extends Animal>

上界通配符 · 它是生产者

能Animal a = list.get(0)
不能list.add(new Dog())
不能list.add(new Animal())

编译器只知道元素"至少是 Animal"，但不知道具体是 Dog 还是 Cat，所以不敢让你往里放。

List<? super Dog>

下界通配符 · 它是消费者

能list.add(new Dog())
能list.add(new Husky())
不能Dog d = list.get(0)

编译器只知道"容器能装 Dog"，但取出来可能是 Animal 或 Object，所以只能读成 Object。

① 为什么 ? extends 不能写

List<? extends Animal> list = new ArrayList<Dog>();
// 如果能 add(new Cat())，这个 Dog 列表里就混进了 Cat —— 类型系统崩塌
list.add(new Cat());   // 编译错误，正是为了拦住上面这种情况

唯一能 add 的是 null（它属于所有类型）。

② 为什么 ? super 读出来只能是 Object

List<? super Dog> list = new ArrayList<Animal>();
Object o = list.get(0);        // 只能这样
Dog d = list.get(0);           // 编译错误：可能是 Animal

③ JDK 里的标准例子

// src 只被读出来（生产）→ extends；dest 只被写进去（消费）→ super
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T t : src) dest.add(t);
}

这句签名是 PECS 最经典的教材，值得背下来当例子用。

④ 无界通配符 <?> 的用途

void printAll(List<?> list) {           // 能接收 List<String>、List<Integer>…
    for (Object o : list) System.out.println(o);
}
// 注意：void printAll(List<Object>) 不行！List<String> 不是 List<Object> 的子类型

这是泛型不变性（invariance）：List<String> 和 List<Object> 没有继承关系，所以要用 <?> 或 <? extends Object>。

记住这个口诀

Producer Extends —— 你要从里面读数据，用 extends。
Consumer Super —— 你要往里面写数据，用 super。
既是生产者又是消费者（既要读又要写）—— 别用通配符，用精确类型 <T>。

04 / PRACTICE

任务 2：统一返回 Result<T>

这是后端项目里出场率最高的泛型类：用一个类型参数承载"成功时的数据"，同时把错误码和错误信息收进同一个结构。

public final class Result<T> {

    private final boolean success;
    private final String code;
    private final String message;
    private final T data;

    private Result(boolean success, String code, String message, T data) {
        this.success = success; this.code = code;
        this.message = message; this.data = data;
    }

    // 泛型方法：类型参数由调用方推断
    public static <T> Result<T> ok(T data) {
        return new Result<>(true, "0", "成功", data);
    }
    public static <T> Result<T> fail(String code, String msg) {
        return new Result<>(false, code, msg, null);
    }

    // 关键：map 让"成功才转换"变得类型安全
    public <R> Result<R> map(Function<T, R> fn) {
        return success ? Result.ok(fn.apply(data))
                        : Result.fail(code, message);
    }

    // 失败时提供兜底值，避免调用方到处判空
    public T orElse(T fallback) { return success ? data : fallback; }

    public boolean isSuccess() { return success; }
    public T getData() { return data; }
}

① 成功链路

Result<Order>.ok(order)
→
.map(Order::getId)
→
Result<Long>

map 的类型参数 R 由传入的函数推断，Result<Order> 变成 Result<Long>，全程编译期检查。

② 失败链路自动短路

Result.fail("4001","库存不足")
→
.map(...) 不执行
→
原样返回失败

这就是在 Java 里模拟"要么值、要么错误"的最小方案（类似 Rust 的 Result / Scala 的 Either）。

③ 为什么用泛型而不是 Object

// 用 Object：调用方必须强转，且编造不出类型错误提示
Order o = (Order) result.getData();   // 运行时才可能 CCE

// 用泛型：类型在签名里，IDE 和编译器都帮你检查
Order o = result.getData();              // 无强转，编译期保证

05 / EXCEPTION

异常体系：Error 不是给你 catch 的

Java 的异常体系只有三个关键词：Throwable 是根，Error 表示系统级崩溃，Exception 才是程序该处理的。而 Exception 又分受检和非受检两类。

Throwable所有可抛出物的根，有 getMessage / printStackTrace / getCause
ErrorJVM 层面问题，程序无力恢复 → 不要 catch
OutOfMemoryErrorStackOverflowErrorNoClassDefFoundError
Exception程序应该处理的问题
受检异常（Checked）必须 try-catch 或 throws 声明
IOExceptionSQLExceptionInterruptedExceptionClassNotFoundException
RuntimeException（非受检）编译期不强制处理，通常是代码 bug
NullPointerExceptionIllegalArgumentExceptionIllegalStateExceptionClassCastException
IndexOutOfBoundsExceptionConcurrentModificationExceptionArithmeticException

受检 vs 非受检，怎么记

受检编译器能预见、调用方有可能合理处理的外部问题：文件不存在、网络断开、数据库连不上
非受检通常是编程错误：空指针、数组越界、参数非法。这类错误应该改代码，而不是 catch
判断法问自己："调用方拿到这个异常，能做出有意义的补救动作吗？" 能 → 受检；不能 → 非受检

为什么业务异常几乎都设计成 RuntimeException

如果 BizException extends Exception，那么每一层调用都得 throws 或 try-catch，方法签名会被污染，代码全是噪音。改成 RuntimeException 后，异常可以沿调用链自然上抛，最终由全局异常处理器统一转成 JSON 返回——这是 Spring Boot 项目的标准做法。

受检异常的典型写法

// 两种处理方式，二选一，不能都不做
public void read1(String path) throws IOException {   // ① 抛给上层
    Files.readString(Path.of(path));
}

public void read2(String path) {                       // ② 当场处理
    try {
        Files.readString(Path.of(path));
    } catch (IOException e) {
        throw new UncheckedIOException("读取失败: " + path, e);  // 转成非受检，保留 cause
    }
}

06 / FINALLY

finally 与 return 的三个陷阱

这段代码面试出现频率极高，因为它能同时考察执行顺序、值传递、以及 finally 的语义。

① finally 一定会执行吗？

try { return 1; } finally { System.out.println("finally"); }

会。除了 System.exit()、Runtime.halt()、JVM 崩溃、以及守护线程被终止这几种情况，finally 都会执行。

② 陷阱一：finally 里修改基本类型，无效

static int f() {
    int x = 1;
    try { return x; }      // 返回值已确定为 1（值拷贝）
    finally { x = 2; }     // 改的是局部变量，返回值不受影响
}
// f() == 1

这就是 D1 讲的"值传递"在字节码层面的体现：return 的值在进入 finally 之前就已被复制到返回槽。

③ 陷阱二：finally 里写 return，会覆盖

static int g() {
    try { return 1; }
    finally { return 2; }   // 直接覆盖前一个返回值
}
// g() == 2

更糟的是：如果 try 里抛了异常，finally 里的 return 会吞掉异常，问题彻底消失，极难排查。

④ 陷阱三：引用类型会"看似"被修改

static StringBuilder h() {
    StringBuilder sb = new StringBuilder("a");
    try { return sb; }
    finally { sb.append("b"); }   // 顺着地址改对象 → 生效
}
// 返回的 StringBuilder 内容是 "ab"

又是 D1 的值传递：返回的是引用副本，但指向同一个对象，所以 finally 里的内容修改能看见。

这就是为什么 D1 的值传递必须真正理解——它在这里、在 D2 的 HashMap、在 D3 的迭代器里反复出现。

铁律

永远不要在 finally 里写 return、break、continue，也不要抛异常。finally 只用来做资源清理。

07 / RESOURCES

try-with-resources：资源安全关闭

手写 finally 关闭资源有三个坑：忘记关、关的时候抛异常覆盖了原异常、多个资源关闭顺序写错。try-with-resources 一次全解决。

老写法 · 三个坑
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader(f));
    return br.readLine();
} catch (IOException e) {
    throw e;
} finally {
    if (br != null) {
        try { br.close(); }
        catch (IOException ignore) { }  // 吞掉
    }
}
新写法 · 自动关闭
try (BufferedReader br =
        new BufferedReader(new FileReader(f))) {
    return br.readLine();
}
// 无需 finally，关闭异常不会覆盖业务异常

① 关闭顺序是「逆序」

try (A a = new A(); B b = new B(); C c = new C()) {
}
// 关闭顺序：C → B → A（后声明的先关，像栈）

编译器会生成嵌套的 try-finally，等价于一层层往里包。

② 关键：suppressed 异常

try (Conn c = open()) {
    throw new RuntimeException("业务异常");   // 主异常
}
// close() 时也抛了异常 → 不会覆盖主异常，而是挂到 
// e.getSuppressed()[0]，主异常照常抛出

用 getSuppressed() 取回被抑制的异常。这是老写法最容易丢信息的地方。

③ 能自动关闭的前提：实现 AutoCloseable

public interface AutoCloseable { void close() throws Exception; }
public interface Closeable extends AutoCloseable { void close() throws IOException; }

// 自己写资源类时，实现它就能用 try-with-resources
class MyConn implements AutoCloseable {
    public void close() { System.out.println("closed"); }
}

④ Java 9+：可以用已有的 final 变量

BufferedReader br = getReader();
try (br) {          // 直接复用变量，不用再声明
    br.readLine();
}

08 / CUSTOM

自定义异常体系

这部分直接决定你项目的"错误可诊断性"。一个好的异常体系应该做到：错误码可归类、message 带上下文、cause 不丢失、全局统一出口。

三层设计

// ① 错误码：用枚举，别用魔法字符串
public enum ErrorCode {
    INVALID_PARAM("4001", "参数不合法"),
    STOCK_NOT_ENOUGH("4002", "库存不足"),
    ORDER_NOT_FOUND("4004", "订单不存在"),
    SYSTEM_ERROR("5000", "系统繁忙");

    private final String code;
    private final String message;
    ErrorCode(String c, String m) { this.code = c; this.message = m; }
    public String code() { return code; }
    public String message() { return message; }
}

// ② 业务异常：非受检，携带错误码与上下文
public class BizException extends RuntimeException {
    private final ErrorCode errorCode;

    public BizException(ErrorCode code) { super(code.message()); this.errorCode = code; }
    public BizException(ErrorCode code, String detail) {
        super(code.message() + ": " + detail);
        this.errorCode = code;
    }
    public BizException(ErrorCode code, String detail, Throwable cause) {
        super(code.message() + ": " + detail, cause);   // 保留 cause，堆栈不丢
        this.errorCode = code;
    }
    public ErrorCode getErrorCode() { return errorCode; }
}

// ③ 使用：在业务校验处抛，在全局处理器统一转
if (stock < qty) throw new BizException(ErrorCode.STOCK_NOT_ENOUGH,
        "商品 " + sku + " 剩余 " + stock);

① 异常沿调用链上抛

Service 抛 BizException
↑
Controller 不 catch
↑
全局处理器捕获

因为是非受检异常，中间层不需要写任何 throws，代码保持干净。

② 全局处理器统一转换

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        log.warn("业务异常: {}", e.getMessage());   // warn：可预期，不打堆栈
        return Result.fail(e.getErrorCode().code(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("未预期异常", e);                  // error：打完整堆栈
        return Result.fail("5000", "系统繁忙");   // 不把内部细节暴露给前端
    }
}

③ 日志级别的选择规则

warn业务异常（库存不足、参数非法）—— 可预期，不打堆栈，避免日志爆炸
error系统异常（NPE、SQL 异常）—— 打完整堆栈 + 上下文，需要人介入
禁止e.printStackTrace() —— 输出到 stderr，不进日志系统，生产环境等于没记录

异常使用的五条纪律

不要吞空的 catch 块是 bug 制造机。至少 log 或重新抛出
不要只打印再抛log.error(...); throw e; 会导致重复记录
用异常做流程用异常控制正常流程性能极差（fillInStackTrace 开销大），该用返回值判断
丢失 causethrow new X(e.getMessage()) 会丢掉原始堆栈，一定要传 cause
粒度过细每个方法都 try-catch 只会让代码难读，异常应该让它在合适的层级被统一处理

关于异常性能的一个准确说法

异常的抛出代价高（要填充堆栈），但 try-catch 块本身在 JVM 上是零成本的（不产生字节码指令，只记录异常表）。所以"加了 try-catch 会变慢"是错的，真正慢的是抛。

09 / SELF CHECK

今天的自测

泛型和异常的题偏概念，答的时候要能给出例子。

什么是类型擦除？举例说明它的影响。

泛型信息只存在于编译期，编译后类型参数被替换为上界（默认 Object），并在调用处插入强制转换。影响：List<String> 与 List<Integer> 运行时是同一个类；不能 new T()、不能 instanceof T、不能用 T.class、静态成员不能用 T、f(List<String>) 与 f(List<Integer>) 不能重载。

为什么 Java 要设计成擦除而不是像 C# 那样具体化？

为了向后兼容。Java 5 引入泛型时，要保证编译产物能在旧 JVM 上运行，并让泛型代码与非泛型旧类库二进制兼容。C# 的具体化泛型需要修改 CLR 运行时。

什么是桥接方法？为什么会有它？

子类继承泛型父类并重写方法时，擦除后父类方法签名是 Object get()，子类是 String get()，签名不一致就无法构成重写。编译器会生成一个合成的桥方法 Object get(){ return get(); } 来维持多态。反射中可通过 isBridge() 识别。

PECS 是什么意思？

Producer Extends, Consumer Super。只读取元素（生产者）用 <? extends T>；只写入元素（消费者）用 <? super T>。典型案例：Collections.copy(List<? super T> dest, List<? extends T> src)。

为什么 List<? extends Animal> 不能 add？

因为它可能是 List<Dog>，也可能是 List<Cat>。若允许 add Animal，就会把 Cat 放进 Dog 列表，破坏类型安全。唯一能 add 的是 null。

为什么 List<String> 不能赋给 List<Object>？

泛型是不变的（invariant）。如果能赋值，就可以通过 List<Object> 往里 add Integer，再按 String 取出，造成 ClassCastException。这正是泛型存在的意义。要接收任意类型用 List<?>。

Error 和 Exception 的区别？

Error 表示 JVM 层面的严重问题（OOM、栈溢出），程序无法恢复，不应该 catch；Exception 表示程序可以处理的问题，分为受检异常（必须处理）和 RuntimeException（编程错误，不强制捕获）。

受检异常和非受检异常怎么选？

问"调用方能否做出有意义的补救"：能（重试、换文件、提示用户）→ 受检；只是编程错误 → RuntimeException。业务异常通常设计成 RuntimeException，避免污染方法签名，由全局处理器统一转换。

为什么 finally 里不要写 return？

① 会覆盖 try 里的返回值；② 会吞掉 try 中抛出的异常，导致问题彻底消失；③ 与 finally 的语义（清理）不符。同理不要写 break/continue，也不要抛异常。

try{return x;} finally{x=2;} 返回什么？

返回原值。return 的表达式在进入 finally 前已求值并保存到返回槽，finally 里修改局部变量不影响它。但若 x 是引用类型且 finally 里修改对象内容，则能看见——因为改的是同一个对象。

try-with-resources 相比 finally 好在哪？

① 自动关闭，不会忘记；② 关闭顺序明确（逆序）；③ 关闭时抛的异常作为 suppressed 附加到主异常，不会覆盖原始业务异常；④ 代码更短。前提是资源实现了 AutoCloseable。

什么是 suppressed 异常？

try-with-resources 中，若 try 块抛了主异常、close() 又抛了异常，后者不会覆盖前者，而是记录在主异常的 getSuppressed() 数组里。老写法用 finally 手动 close 时，close 的异常会覆盖业务异常，丢失真正的错因。

什么时候不该用异常？

① 用异常控制正常流程（性能差且难读）；② 可预期的业务分支（用返回值/Result 更合适）；③ 只为了打日志而 catch 再抛出。异常应该用于"真正的异常情况"。
