01 / COORDINATE

坐标与仓库：Maven 的地基

Maven 用三元组定位一切：groupId : artifactId : version。你写下的每个依赖，都是按这个地址去仓库里取。

坐标三要素

groupId组织名，反写域名：org.springframework
artifactId项目名：spring-core
version版本：6.1.0
packagingjar / war / pom（默认 jar）

三类仓库

本地~/.m2/repository，先查这里
远程中央仓库 / 私服（Nexus、Artifactory）
查找顺序本地 → 私服 → 中央，找到就缓存到本地
<!-- 用私服加速并缓存，企业内网标准配置 -->
<mirror>
  <id>nexus</id>
  <mirrorOf>*</mirrorOf>
  <url>https://nexus.company.com/repository/maven-public/</url>
</mirror>

国内常见问题：中央仓库慢 → 配阿里云镜像；公司内网 → 配私服，注意 mirrorOf 别把私服本身也镜像了。

02 / CONFLICT

依赖冲突：谁赢谁输

A 依赖 C-1.0，B 依赖 C-2.0，项目同时引入 A 和 B——最后用哪个版本？Maven 有两条例外规则决定。

① 冲突现场　两条路径都通向 C，但版本不同。

order-service
├─ A : 1.0
│　└─ C : 1.0
└─ B : 1.0
　 └─ C : 2.5

② 规则一：最短路径优先　距离项目最近的胜出。

order-service
├─ A : 1.0
│　└─ C : 1.0 ← 深度 2，胜出
└─ B : 1.0
　 └─ C : 2.5 深度 2，但先声明

深度不同时，浅的赢。比如直接依赖 C-3.0（深度 1）会赢过任何传递依赖。

③ 规则二：同深度时，先声明优先　pom 里写在前面的人赢。

<!-- 谁写在前面，就用谁带进来的 C --><dependency><artifactId>A</artifactId></dependency>
<dependency><artifactId>B</artifactId></dependency>

这条规则很脆弱——调整一下顺序行为就变了，所以真实项目从不依赖它。

④ 正解：用 dependencyManagement 显式锁定

<!-- 父 pom：只声明版本，不引入依赖 -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.alibaba</groupId>
      <artifactId>fastjson2</artifactId>
      <version>2.0.43</version>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 子模块：不写 version，继承父的 -->
<dependency>
  <groupId>com.alibaba</groupId>
  <artifactId>fastjson2</artifactId>
</dependency>

这是唯一可靠的版本治理手段，Spring Boot 的 parent 就是这么做的（BOM）。

0 / 4

排查冲突的三个命令

mvn dependency:tree                                  // 看完整依赖树
mvn dependency:tree -Dincludes=com.alibaba:fastjson2 // 只看某个包从哪来
mvn dependency:analyze                               // 找出"声明了但没用"和"用了但没声明"

典型症状：NoSuchMethodError / NoClassDefFoundError

运行时突然报某个类找不到方法，八成是低版本覆盖了高版本（Maven 按最短路径选了旧版）。
排查步骤：① dependency:tree 确认实际版本；② 找到引入旧版的依赖，加 <exclusions> 排除；③ 或在 dependencyManagement 里强制指定版本。

03 / SCOPE

六种作用域：决定打包与可见性

作用域控制两件事：这个依赖在哪些阶段可用、会不会打进最终包。搞错会直接导致"本地能跑、上线就崩"。

scope编译测试运行打进包典型用途
compile（默认）✓✓✓✓Spring、Jackson 等核心依赖
provided✓✓✗✗Servlet API、Lombok（容器/编译期提供）
runtime✗✓✓✓JDBC 驱动、日志实现
test✗✓✗✗JUnit、Mockito
system✓✓✓✗本地 jar 路径（不推荐）
import只用于 dependencyManagement 中导入 BOMSpring Boot BOM

两个高频事故

provided 打成 jarServlet API 用了 provided 就对了；如果写成 compile，会和 Tomcat 自带的冲突
test 依赖泄漏JUnit 写成了 compile，被打进生产包，可能拖入一堆传递依赖

典型 pom 结构

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>

  <dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <scope>provided</scope>          <!-- 容器提供 -->
  </dependency>

  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>              <!-- 只在测试期 -->
  </dependency>
</dependencies>

04 / LIFECYCLE

生命周期：三套阶段

Maven 有三条独立的生命周期：clean、default、site。执行某个阶段时，它前面的所有阶段都会自动执行。

CLEAN
clean
删 target
→
VALIDATE
validate
校验工程
→
COMPILE
compile
编主代码
→
TEST
test
跑单测
→
PACKAGE
package
打 jar
→
INSTALL
install
装本地库
→
DEPLOY
deploy
推私服

执行 mvn install 时，validate→compile→test→package→install 全部会跑一遍。

0 / 7

插件是怎么挂上去的

生命周期本身只是"阶段名"，真正干活的是插件目标，通过 <executions> 绑定到某个阶段。

<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration><release>17</release></configuration>
</plugin>
<plugin>
  <artifactId>maven-surefire-plugin</artifactId>   <!-- 跑测试的插件 -->
  <configuration>
    <skipTests>false</skipTests>
  </configuration>
</plugin>

三个常用跳过参数，别搞混

-DskipTests跳过执行，但仍然编译测试代码（常用）
-Dmaven.test.skip完全不编译也不执行（更快）
-o离线模式，只用本地仓库

05 / MULTI-MODULE

多模块：继承与聚合

两个概念经常被混为一谈：继承是子模块拿到父的配置，聚合是父模块能一键构建所有子模块。

聚合（父 pom）

<packaging>pom</packaging>
<modules>
  <module>order-domain</module>
  <module>order-service</module>
  <module>order-web</module>
</modules>

在父目录执行 mvn install，会按依赖顺序构建所有模块。

继承（子 pom）

<parent>
  <groupId>com.demo</groupId>
  <artifactId>order-parent</artifactId>
  <version>1.0.0</version>
</parent>

子模块不需要重复写 groupId/version，也继承 dependencyManagement。

一个合理的分层

order-parent          <!-- 统一版本、插件、编码 -->
├── order-domain      <!-- 实体、值对象、领域异常，不依赖 Spring -->
├── order-service     <!-- 业务逻辑，依赖 domain -->
├── order-web         <!-- Controller、启动类，依赖 service -->
└── order-infra       <!-- 数据库、MQ 实现 -->

依赖方向必须单向：web → service → domain。domain 不能反过来依赖 service，这是整洁架构的底线。

多模块最常见的报错

Could not find artifact com.demo:order-domain:1.0.0
原因：子模块之间互相依赖时，被依赖的模块还没 install 到本地仓库。
解决：在父目录执行 mvn install（而不是在子模块里 mvn compile），保证构建顺序正确。

06 / JUNIT

JUnit 5：结构变了

JUnit 5 和 4 完全是两套东西：注解包名变了、断言支持 Lambda、还多了参数化测试。别混用。

JUnit 4

@Test(expected = Exception.class)
@Before / @After
@BeforeClass / @AfterClass
@RunWith(SpringRunner.class)

JUnit 5

@Test + assertThrows(...)
@BeforeEach / @AfterEach
@BeforeAll / @AfterAll
@ExtendWith(SpringExtension.class)

一个完整的测试类

class OrderServiceTest {

    private OrderRepository repo;
    private OrderService service;

    @BeforeEach                     // 每个测试方法前执行，保证隔离
    void setUp() {
        repo = Mockito.mock(OrderRepository.class);
        service = new OrderService(repo);
    }

    @Test
    @DisplayName("库存不足时应抛出业务异常")
    void shouldThrowWhenStockNotEnough() {
        Mockito.when(repo.stockOf("SKU1")).thenReturn(0);

        BizException ex = assertThrows(BizException.class,
                () -> service.create("SKU1", 2));
        assertEquals(ErrorCode.STOCK_NOT_ENOUGH, ex.getErrorCode());
    }

    @ParameterizedTest            // 参数化：一个方法测多组数据
    @CsvSource({"0,false", "1,true", "99,true"})
    void testPayable(int qty, boolean expected) {
        assertEquals(expected, qty > 0);
    }
}

断言的三条实践

带消息assertEquals(expect, actual, "创建订单后状态应为 CREATED")，失败时省一半排查时间
断言异常别用 try-catch 吞，用 assertThrows 并检查异常类型和消息
一个测试一个主题一个方法里断言 10 件事，失败时不知道哪件坏了

07 / MOCKITO

Mockito：隔离外部依赖

单元测试的核心要求是只测一个类。数据库、HTTP、MQ 全部 fake 掉，否则测试会慢、会不稳定、会互相影响。

① 造一个假依赖

OrderRepository repo = Mockito.mock(OrderRepository.class);
// 此时 repo 的所有方法都返回默认值（null / 0 / false）

② 打桩：指定输入对应的输出

Mockito.when(repo.stockOf("SKU1")).thenReturn(0);
Mockito.when(repo.save(Mockito.any())).thenAnswer(inv -> inv.getArgument(0));

any() 是参数匹配器；一旦用了匹配器，所有参数都得用匹配器。

③ 执行被测方法

try {
    service.create("SKU1", 2);
} catch (BizException e) {
    assertEquals(ErrorCode.STOCK_NOT_ENOUGH, e.getErrorCode());
}

④ 验证交互，而不只是结果

Mockito.verify(repo, Mockito.never()).save(Mockito.any());
ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);
Mockito.verify(repo).save(captor.capture());
assertEquals(new BigDecimal("198.00"), captor.getValue().getTotal());

verify(never()) 断言"没被调用"，这在测校验逻辑时特别有用。

0 / 4

Mockito 的四个限制

final 类/方法老版本不能 mock，需要 mockito-inline（现在已内置 inline mock maker）
static 方法需要 mockStatic（Spring Boot 3.4 起不再推荐，尽量重构）
private 方法不能 mock。这是设计味道，说明该方法该抽出去
构造器不能 mock new，需要工厂或依赖注入

另一条路是 spy：对真实对象打桩，未打桩的方法走真实实现。Mockito.spy(realObj)。它常被滥用，因为"只测一半"往往意味着设计有问题。

08 / LAYERS

测试金字塔：别写反了

测试不是越多越好，而是比例要对。倒金字塔（一堆端到端测试）是团队效率的头号杀手。

① 单元测试（70%）　测单个类，外部依赖全 mock，毫秒级。

单元测试快、稳、定位准 · 占大头
集成测试真连数据库/容器
端到端测试起服务、走 HTTP

② 集成测试（20%）　验证"SQL 写对了没""序列化对不对"，需要真实中间件。

用 Testcontainers 起一个真实的 MySQL/Redis 容器，比 H2 内存库更接近生产（H2 的 SQL 方言和 MySQL 有差异，容易假绿）。

③ 端到端（10%）　只覆盖最关键的几条主流程，如"下单→支付→完成"。

单元测试
集成测试
端到端测试慢、脆、但最接近用户

④ 反模式：冰淇淋筒

大量手工测试 + 大量端到端，单元测试几乎没有。结果是：跑一次要半小时、挂了不知道哪坏、改一行代码要修十个测试，最后没人愿意跑。

0 / 4

单测的边界：测什么、不测什么

该测不该测
业务规则（库存判断、金额计算、状态流转）getter / setter
边界条件（0、负数、null、超限）纯框架代码（Spring 自己）
异常分支（该抛的有没有抛）私有方法（通过公开方法间接覆盖）
并发/幂等关键点（必要时）实现细节（内部调了哪个方法）

判断标准

问一句："如果我重构这个方法内部实现（行为不变），这个测试会不会挂？"
会 → 你测的是实现而不是行为，该改。测试应该保护行为契约，而不是锁死实现。

09 / SELF CHECK

今天的自测

Maven 依赖冲突的两条调解规则？

① 最短路径优先（离项目更近的胜出）；② 路径长度相同时，pom 中先声明的胜出。可靠做法是用 dependencyManagement 显式锁定版本。

dependencyManagement 和 dependencies 的区别？

dependencies 是真正引入依赖；dependencyManagement 只声明版本（不引入），子模块引用时不写 version 就继承这里的版本。Spring Boot 的 parent 就是通过它统一管理版本（BOM）。

compile、provided、runtime、test 的区别？

compile：全程可用且打包；provided：编译和测试可用，运行时由容器提供、不打包（Servlet API）；runtime：编译不可用、运行和打包可用（JDBC 驱动）；test：仅测试阶段可用（JUnit）。

mvn package 和 mvn install 的区别？

package 只打 jar 到 target；install 会先执行 package，再把 jar 安装到本地仓库 ~/.m2，供其他模块依赖。多模块项目必须在父目录执行 install。

-DskipTests 和 -Dmaven.test.skip 的区别？

skipTests 跳过测试执行但仍编译测试代码；maven.test.skip 完全不编译也不执行，更快。CI 上想省时间用后者。

多模块里父子 pom 的"继承"和"聚合"分别是什么？

聚合：父 pom 用 <modules> 列出子模块，能一键构建全部；继承：子 pom 用 <parent> 复用父的配置（版本、插件、依赖管理）。两者常同时使用但概念不同。

JUnit 5 相对 JUnit 4 的主要变化？

包名从 org.junit 改为 org.junit.jupiter；@Before/@After 改为 @BeforeEach/@AfterEach；@BeforeClass 改为 @BeforeAll；断言异常用 assertThrows 替代 expected 属性；新增参数化测试 @ParameterizedTest；扩展机制用 @ExtendWith 替代 @RunWith。

什么时候该用 mock，什么时候不该？

该用：外部不可控依赖（数据库、HTTP、MQ、时间、随机数）。不该用：被测类自身、值对象、简单的 POJO。过度 mock 会导致测试只验证"调用顺序"，重构即挂。

Mockito 里 mock 和 spy 的区别？

mock 创建完全假的替身，所有方法返回默认值；spy 包装真实对象，未打桩的方法走真实实现，打桩的用指定返回值。spy 常用于测试遗留代码，但容易掩盖设计问题。

为什么说测试金字塔不能倒过来？

端到端测试慢、脆弱、失败定位难。如果大部分逻辑只靠 E2E 覆盖，反馈周期会从秒级变成分钟级，且一次失败无法定位到具体类。应让单元测试占大头，E2E 只覆盖关键主流程。

如何判断一个单测写得对不对？

关键问题："重构内部实现（行为不变）时它会挂吗？"挂了说明测的是实现细节。好的测试只依赖公开 API 和可观察行为，失败信息能直接指出哪里不符合预期。
