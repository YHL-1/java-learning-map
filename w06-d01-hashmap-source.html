01 / FIELDS

五个常量 + 四个字段

面试问"HashMap 的默认值"，能报出这五个数字就说明读过源码；能说清每个数字为什么是这个值，才说明理解了。

16DEFAULT_INITIAL_CAPACITY，默认容量。必须是 2 的幂（后面讲原因）
1<<30MAXIMUM_CAPACITY，最大容量。int 最大是 2³¹-1，取 2³⁰ 是为了让 (n-1)&hash 的掩码还在正数范围
0.75DEFAULT_LOAD_FACTOR，负载因子。空间与冲突的折中
8TREEIFY_THRESHOLD，链表转树的阈值
6UNTREEIFY_THRESHOLD，树退化为链表的阈值。比 8 小 2，留缓冲避免 7/8 之间反复转换
64MIN_TREEIFY_CAPACITY，能树化的最小容量。容量不够时优先扩容
transient Node<K,V>[] table;   // 桶数组，长度永远是 2 的幂
transient int size;              // 实际元素个数（不是数组长度）
transient int modCount;          // 结构性修改次数，供 fail-fast 用
int threshold;                    // 扩容阈值 = capacity * loadFactor
final float loadFactor;           // 负载因子，构造时确定后不可变

一个容易记混的点：容量 ≠ 元素个数

capacity 是数组长度（桶的数量），size 是元素个数，threshold = capacity × 0.75。
16 个桶的 HashMap，存到第 13 个元素时才扩容（size > 12）。

02 / TABLESIZEFOR

tableSizeFor：向上取最近的 2 的幂

你写 new HashMap(17)，实际容量会被调整成 32。这个"向上取整"用的是五次移位或运算，是源码里最漂亮的一段。

static final int tableSizeFor(int cap) {
    int n = cap - 1;                    // ← 为什么先减 1？
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}

① 原理：把最高位之后全部填 1　以 cap=17 为例，n=16（10000）。

n = 16 = 0001 0000

每做一次 n |= n >>> k，就把已有的最高位往右复制 k 位。

② 五次移位，把 1 个 1 变成一串 1

n = 0001 0000
n |= n>>>1   → 0001 1000
n |= n>>>2   → 0001 1110
n |= n>>>4   → 0001 1111
n |= n>>>8   → 0001 1111
n |= n>>>16  → 0001 1111
return n + 1 → 0010 0000 = 32 ✅

为什么是 1/2/4/8/16？因为 int 只有 32 位，等比翻倍正好覆盖全部。

③ 关键：为什么先 cap - 1

如果 cap 本身已是 2 的幂（比如 16），不减 1 会发生什么？

n = 16 = 0001 0000
填 1 后 → 0001 1111 = 31
return 31 + 1 = 32   // ❌ 翻倍了！

// 减 1 之后：
n = 15 = 0000 1111
填 1 后 → 0000 1111 = 15
return 15 + 1 = 16   // ✅ 保持原值

一句话：减 1 是为了让"已经是 2 的幂"的输入不会被翻倍。

0 / 3

注意：这个值只在第一次 put 时才真正生效

new HashMap(17) 时 table 还是 null，只是把 threshold 记成了 32。
第一次 put 调 resize()，才用这个 threshold 当容量建数组，然后把 threshold 改成 容量 × 0.75。
所以"预估容量"这个技巧要写对：new HashMap<>((int)(expected / 0.75f) + 1)。

03 / HASH

扰动函数：h ^ (h >>> 16)

一句话：把高 16 位的信息掺到低 16 位里，因为定位桶只用到低位。

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

为什么需要它

桶定位用的是 (n-1) & hash。当 n=16 时，掩码是 1111，只用到 hash 的最低 4 位，高 28 位完全被丢弃。

如果一组 key 的 hashCode 恰好"低位相同、高位不同"（现实中很常见，比如某些自增 ID 左移、或者 hash 分布不均的字符串），它们就会全部挤到同一个桶里，退化成链表。

异或高 16 位之后，高位信息参与进来，低位变得"更随机"，分布更均匀。

JDK 7 的做法（更复杂）

h ^= (h >>> 20) ^ (h >>> 12);
h ^= (h >>> 7) ^ (h >>> 4);

四次移位异或，效果类似但更慢。JDK 8 简化成一次，因为树化已经能兜底极端冲突。

为什么是异或不是与/或

a & b  → 结果偏 0（丢失信息）
a | b  → 结果偏 1（丢失信息）
a ^ b  → 0/1 各半，信息保留最好

异或是唯一"两个输入都能影响每一位输出"的位运算。

一个反直觉的细节

对小整数来说，扰动是"无效"的：hash(58) = 58 ^ 0 = 58，因为高 16 位全是 0。
所以 Integer 做 key 时，扰动没起作用——但也无所谓，因为 int 的低位分布本来就好。
扰动主要救的是那些 hashCode 高位有信息、低位是常量的类（比如某些用地址派生 hash 的对象）。

04 / PUTVAL

putVal 逐行

这是 HashMap 的主干方法，60 行左右。面试说"讲一下 put"，能把这段的结构说出来就够了。

final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;

    // ① 懒初始化
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;

    // ② 定位桶，空则直接放
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);

    else {
        Node<K,V> e; K k;
        // ③ 首节点就是目标 key → 覆盖
        if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
            e = p;
        // ④ 红黑树插入
        else if (p instanceof TreeNode)
            e = ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);
        // ⑤ 遍历链表，尾插
        else {
            for (int binCount = 0; ; ++binCount) {
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);
                    if (binCount >= TREEIFY_THRESHOLD - 1)  // ≥ 7，即第 9 个
                        treeifyBin(tab, hash);
                    break;
                }
                if (e.hash == hash && (e.key == key || (key != null && key.equals(e.key))))
                    break;
                p = e;
            }
        }
        if (e != null) {   // 覆盖已有 key
            V oldValue = e.value;
            if (!onlyIfAbsent || oldValue == null) e.value = value;
            afterNodeAccess(e);
            return oldValue;    // ← 覆盖时返回旧值
        }
    }
    ++modCount;
    if (++size > threshold) resize();
    afterNodeInsertion(evict);
    return null;             // ← 新增时返回 null
}

三个只读源码才会知道的细节

① treeify 条件代码里是 binCount >= 7，不是 8。因为 binCount 从 0 开始数，等于 7 时是第 9 个节点——插入后才判断，所以链表现在长度是 9？不对：
实际语义是"链表长度达到 8 时尝试树化"。面试答 8 是标准答案，但要能解释这个 ±1 的来历。
② 返回值新增返回 null，覆盖返回旧值。所以 put 可以被用来"原子地取出旧值"
③ 比 hash 在前p.hash == hash && ...——hash 不等直接短路，避免昂贵的 equals

为什么 JDK 8 改成尾插

JDK 7 用头插（新节点放链表头部），代码简单，但在并发扩容时会导致链表反转，进而形成环——这是下一节要讲的著名事故。尾插彻底避免了这个问题（但依然不是线程安全的）。

05 / RESIZE

resize：高低位拆分

扩容不是"重新算 hash 再放一遍"，而是把一条链表劈成两条，分别挂到原位和原位+oldCap。这是 JDK 8 最重要的性能优化之一。

final Node<K,V>[] resize() {
    Node<K,V>[] oldTab = table;
    int oldCap = (oldTab == null) ? 0 : oldTab.length;
    int oldThr = threshold;
    int newCap, newThr = 0;
    if (oldCap > 0) {
        if (oldCap >= MAXIMUM_CAPACITY) { threshold = Integer.MAX_VALUE; return oldTab; }
        else if ((newCap = oldCap << 1) < MAXIMUM_CAPACITY && oldCap >= DEFAULT_INITIAL_CAPACITY)
            newThr = oldThr << 1;          // 阈值也翻倍：12 → 24
    }
    // ... 省略初始化分支
    threshold = newThr;
    Node<K,V>[] newTab = (Node<K,V>[])new Node[newCap];

    for (int j = 0; j < oldCap; ++j) {
        Node<K,V> e;
        if ((e = oldTab[j]) != null) {
            oldTab[j] = null;
            if (e.next == null)
                newTab[e.hash & (newCap - 1)] = e;          // 单节点：直接算新位置
            else if (e instanceof TreeNode)
                ((TreeNode<K,V>)e).split(this, newTab, j, oldCap);
            else {   // ★ 链表：拆成 lo / hi 两条
                Node<K,V> loHead = null, loTail = null;
                Node<K,V> hiHead = null, hiTail = null;
                Node<K,V> next;
                do {
                    next = e.next;
                    if ((e.hash & oldCap) == 0) {        // 第 5 位是 0 → 原位
                        if (loTail == null) loHead = e; else loTail.next = e;
                        loTail = e;
                    } else {                              // 第 5 位是 1 → +oldCap
                        if (hiTail == null) hiHead = e; else hiTail.next = e;
                        hiTail = e;
                    }
                } while ((e = next) != null);
                if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
                if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
            }
        }
    }
    return newTab;
}

② 容量翻倍到 32，掩码变成 11111　多出来的那一位是 oldCap = 16（10000）。

所以元素的新下标只有两种可能：j（第 5 位是 0）或 j + 16（第 5 位是 1）。

k1: hash & 16 = 0   → 留在 3
k2: hash & 16 = 16  → 移到 19
k3: hash & 16 = 0   → 留在 3

④ 为什么这个技巧成立

因为容量是 2 的幂，扩容就是多出一个二进制位。这个位是 0 还是 1，恰好由 hash & oldCap 决定——不用算，直接看那一位。

这是"容量必须是 2 的幂"的第二个理由（第一个是 (n-1)&hash 等价取模）。

扩容的代价（面试常问"扩容很慢吗"）

时间O(n)，要遍历所有桶和节点
内存瞬间需要两份数组，老数组要等 GC
时机在 put 内部同步完成，会阻塞当前线程（这就是为什么"预分配容量"能提升性能）

06 / TREEIFY

树化：两个条件缺一不可

"链表长度到 8 就转红黑树"——这句话只说对了一半，漏了容量条件，是面试最常见的扣分点。

final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)  // 容量 < 64
        resize();                        // ★ 不树化，改成扩容
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // 真正转红黑树
    }
}
条件值不满足时
单桶链表长度≥ 8不触发 treeifyBin
table 容量≥ 64改成 resize()，不树化
退化条件树节点 ≤ 6退回链表

为什么容量小的时候宁可扩容

容量小说明冲突的根源是"桶太少"，而不是"hash 太差"。扩容能把元素打散到更多桶里，比建一棵红黑树更划算——树的维护成本（旋转、比较）远高于一次扩容。

只有容量已经足够大（≥64）、却依然有桶挤了 8 个，才说明是真的 hash 碰撞，这时树化才值得。

为什么阈值是 8

源码注释里给了泊松分布的计算：在负载因子 0.75 下，一个桶里节点数达到 8 的概率约为 0.00000006。
也就是说正常情况下几乎不会树化——树化是给"恶意构造"或"极端 hash"准备的兜底，不是常规路径。

07 / INFINITE LOOP

JDK 7 的死循环事故

这是 Java 史上最著名的 bug 之一：并发 put 导致 HashMap 成环，CPU 打满 100%。理解它，就理解了"为什么 JDK 8 改尾插"和"为什么并发必须用 CHM"。

0 / 5

JDK 8 改尾插就安全了吗？

不会成环了，但仍然会丢数据。两个线程同时 put 时：

  • 都判断某个桶是空的 → 都执行 tab[i] = newNode(...) → 后写的覆盖先写的，一个元素凭空消失
  • 都触发扩容 → 一个线程的迁移结果被另一个覆盖，部分节点丢失
  • size 的 ++ 不是原子操作 → 计数不准

结论：HashMap 在任何 JDK 版本下都不是线程安全的，JDK 8 只是把"死循环"降级成了"数据错乱"。

08 / MINI IMPL

任务 2：手写简化版 HashMap

不写红黑树，只保留核心：数组 + 链表 + 扰动 + 扩容。写完你对 put 流程的记忆会从"背"变成"推导"。

public class MiniHashMap<K, V> {

    static class Node<K, V> {
        final int hash; final K key; V value; Node<K, V> next;
        Node(int h, K k, V v, Node<K, V> n) { hash = h; key = k; value = v; next = n; }
    }

    private Node<K, V>[] table;
    private int size, threshold = 12;
    private static final float LOAD = 0.75f;

    private static int hash(Object k) {
        int h = (k == null) ? 0 : k.hashCode();
        return h ^ (h >>> 16);
    }

    public V put(K key, V value) {
        if (table == null) table = new Node[16];
        int h = hash(key), i = (table.length - 1) & h;
        for (Node<K, V> p = table[i]; p != null; p = p.next) {
            if (p.hash == h && (p.key == key || (key != null && key.equals(p.key)))) {
                V old = p.value; p.value = value; return old;   // 覆盖，返回旧值
            }
        }
        table[i] = new Node<>(h, key, value, table[i]);       // 头插（单线程安全）
        if (++size > threshold) resize();
        return null;
    }

    public V get(Object key) {
        if (table == null) return null;
        int h = hash(key);
        for (Node<K, V> p = table[(table.length - 1) & h]; p != null; p = p.next) {
            if (p.hash == h && (p.key == key || (key != null && key.equals(p.key)))) return p.value;
        }
        return null;
    }

    private void resize() {
        Node<K, V>[] old = table;
        int newCap = old.length << 1;
        Node<K, V>[] nt = new Node[newCap];
        threshold = (int) (newCap * LOAD);
        for (int j = 0; j < old.length; j++) {
            Node<K, V> lo = null, hi = null, e;
            for (e = old[j]; e != null; ) {
                Node<K, V> next = e.next;
                if ((e.hash & old.length) == 0) { e.next = lo; lo = e; }
                else                              { e.next = hi; hi = e; }
                e = next;
            }
            nt[j] = lo;
            nt[j + old.length] = hi;
        }
        table = nt;
    }
}

写这个练习的三个收获

  1. 你会真正记住 (n-1) & hash 为什么等价于取模
  2. 你会明白"头插在单线程下没问题"，问题只出在并发
  3. 你会发现 resize 里 lo/hi 拆分其实就是"按 hash & oldCap 分两堆，再各自头插"——比源码的 tail 版本更好懂

09 / JMH

用 JMH 测初始容量

任务里要求"用 JMH 对比不同初始容量性能"。这个实验的价值不在数字，而在让你亲眼看到扩容次数对吞吐的影响。

@State(Scope.Thread)
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.MILLISECONDS)
@Warmup(iterations = 3, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
public class MapCapacityBench {

    private static final int N = 100_000;

    @Benchmark
    public Map<Integer, Integer> defaultCap() {
        Map<Integer, Integer> m = new HashMap<>();          // 一路扩容到 256K
        for (int i = 0; i < N; i++) m.put(i, i);
        return m;
    }

    @Benchmark
    public Map<Integer, Integer> presized() {
        Map<Integer, Integer> m = new HashMap<>((int)(N / 0.75f) + 1);
        for (int i = 0; i < N; i++) m.put(i, i);
        return m;
    }
}

预期结果与解读

写法扩容次数相对吞吐
new HashMap<>()16→32→…→262144，共 15 次1.0x（基准）
new HashMap<>(133_334)0 次通常 1.3–1.8x

注意：具体倍数取决于 JDK 版本和机器，不要背数字，要能说出"省掉了 15 次 O(n) 迁移"这个原因。

JMH 容易踩的三个坑

① 没用 Blackhole结果没被消费，JIT 可能把整个循环优化掉，测出"无限快"
② 没预热前几轮是解释执行，数字完全不可信。@Warmup 必须加
③ 在同一个 JVM 里跑所有用例JIT 的 profile 会互相污染，必须用 @Fork 隔离

10 / SELF CHECK

今天的自测

这一天的题已经进入"源码级"，答的时候要能说出方法名和关键变量。

HashMap 的五个关键常量分别是什么？

16（默认容量）、1<<30（最大容量）、0.75（负载因子）、8（树化阈值）、6（退化阈值）、64（最小树化容量）——严格说是六个。

tableSizeFor 为什么要先 cap - 1？

如果输入本身已是 2 的幂（如 16），不减 1 会先填成全 1（31），再 +1 就翻倍成 32。减 1 保证"已是 2 的幂"的值不被放大。

扰动函数为什么是 h ^ (h >>> 16)？

定位桶只用 hash 的低位（(n-1)&hash），高 16 位被丢弃。异或高 16 位能把高位信息掺进低位，让分布更均匀，减少碰撞。用异或是因为它保留信息最多。

put 的返回值有什么含义？

新增返回 null；覆盖已有 key 时返回旧值。所以可以用 put 的返回值判断"是不是首次插入"，也可以借它取出旧值。

JDK 8 的 resize 为什么不用重新计算 hash？

容量是 2 的幂，扩容相当于多出一个二进制位。用 e.hash & oldCap 判断这一位是 0 还是 1：0 留在原下标 j，1 移到 j+oldCap。原链表被拆成 lo/hi 两条直接挂上去。

树化的两个条件是什么？为什么容量小时不树化？

链表长度 ≥ 8 且 table 容量 ≥ 64。容量小时冲突的根源是桶太少，扩容打散元素比建树更划算；树的维护成本更高。

退化阈值为什么是 6 不是 8？

留 2 的缓冲带。如果树和链表都在 8 附近转换，会在临界点反复树化/退化，白白消耗 CPU。

JDK 7 的 HashMap 为什么会死循环？

扩容时用头插，链表会被反转。两个线程并发扩容时交错执行，A.next=B 且 B.next=A，链表成环。之后 get 遍历链表永不结束，CPU 100% 且无异常。

JDK 8 改成尾插后，HashMap 就线程安全了吗？

没有。尾插只避免了成环，仍然会丢数据（两个线程同时往空桶写会互相覆盖）、size 计数不准、扩容结果互相覆盖。并发场景必须用 ConcurrentHashMap。

为什么说"容量必须是 2 的幂"有两个理由？

① (n-1) & hash 只有在 n 是 2 的幂时才等价于取模，且掩码全 1 分布均匀；② 扩容时可以用 hash & oldCap 判断元素去留，无需重算 hash。

手写 HashMap 时，头插和尾插哪个好？

单线程下都可以。头插代码更短（tab[i] = new Node(..., tab[i])），但并发下会导致链表反转、成环。JDK 8 选尾插就是为了消除这个隐患，代价是要遍历到链尾。

JMH 里 @Fork 和 @Warmup 为什么必须加？

@Warmup 让 JIT 充分编译后再开始测量，否则测的是解释执行的速度；@Fork 让每个 benchmark 在独立 JVM 里跑，避免 profile 互相污染和状态残留。
