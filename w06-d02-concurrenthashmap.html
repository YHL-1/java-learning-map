02 / JDK7

分段锁：Segment 继承 ReentrantLock

JDK 7 的设计很直白：把一个大的 HashMap 拆成 16 个小的 HashMap，每个小 HashMap 自带一把锁。

final class Segment<K,V> extends ReentrantLock implements Serializable {
    transient volatile HashEntry<K,V>[] table;
    transient int count;
    transient int modCount;
    transient int threshold;
    final float loadFactor;
}

// ConcurrentHashMap 主体
final Segment<K,V>[] segments;   // 默认长度 16

// 定位分两步：先找段，再找段内的桶
int sshift = 0;
int ssize = 1;
while (ssize < concurrencyLevel) { ++sshift; ssize <<= 1; }   // 段数取 2 的幂
segments[(hash >>> segmentShift) & segmentMask].put(key, hash, value, false);

分段锁的根本局限

并发度被写死在段数上。默认 16 段意味着最多 16 个线程同时写——再多也没用。
而且"段"是个静态划分：某个段里热点 key 特别多，其他段空闲也帮不上忙。

03 / JDK8

JDK 8 结构：Node + CAS + synchronized

JDK 8 又回到了"数组 + 链表 + 红黑树"的大结构，但用三种手段保证并发安全：volatile 读、CAS 写空桶、synchronized 锁非空桶。

public class ConcurrentHashMap<K,V> {
    transient volatile Node<K,V>[] table;   // volatile：保证可见性
    private transient volatile int sizeCtl;     // ★ 核心控制变量
    private transient volatile long baseCount;  // 计数
    private transient volatile CounterCell[] counterCells;
}

final V putVal(K key, V value, boolean onlyIfAbsent) {
    if (key == null || value == null) throw new NullPointerException();  // ★ 不允许 null
    int hash = spread(key.hashCode());
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                                    // ① 初始化（CAS 抢）
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;                                            // ② 空桶：CAS 无锁写
        }
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);                           // ③ 正在扩容：帮忙
        else {
            V oldVal = null;
            synchronized (f) {                                   // ④ 锁住桶的首节点
                if (tabAt(tab, i) == f) {
                    // 链表遍历 / 红黑树插入 ...
                }
            }
        }
    }
    addCount(1L, binCount);   // ⑤ 计数 + 可能触发扩容
    return null;
}

为什么 key 和 value 都不能为 null

因为 get 返回 null 有二义性：是"没有这个 key"还是"这个 key 的值就是 null"？
在并发场景下无法用 containsKey 二次确认（这中间可能被别的线程改掉），所以干脆禁止 null。HashMap 允许 null，CHM 不允许，这是高频对比题。

04 / SIZECTL

sizeCtl：一个变量四种含义

这是 JDK 8 CHM 最难懂也最常考的点。同一个 int 字段，在不同取值下代表完全不同的状态。

取值含义
0默认值，table 尚未初始化
-1正在初始化，其他线程要自旋等待
负数且 < -1正在扩容，值为 -(1 + 参与扩容的线程数)
正数扩容阈值（等价于 HashMap 的 threshold）

① 初始化：CAS 抢占 -1

private final Node<K,V>[] initTable() {
    while ((tab = table) == null || tab.length == 0) {
        if ((sc = sizeCtl) < 0)
            Thread.yield();                       // 别人在初始化，让出 CPU 重试
        else if (U.compareAndSwapInt(this, SIZECTL, sc, -1)) {
            // 抢到了，只有我能初始化
            try { ... nt = new Node[n]; table = tab = nt; sizeCtl = n - (n >>> 2); }
            finally { }
            break;
        }
    }
}

n - (n >>> 2) 就是 n * 0.75，全用位运算。

② 扩容：负数表示"有几个线程在帮忙"

// 第一个触发扩容的线程：
sizeCtl = (sc << 1) + 1;   // 高位存新容量，低位 +1 表示有 1 个线程

// 这个线程开始迁移数据后：
sizeCtl = -(1 + n);        // n = 参与迁移的线程数

// 另一个线程发现 sizeCtl < -1 → 知道在扩容 → helpTransfer()

这样"扩容量"和"参与线程数"塞进一个 int，省了同步开销。属于典型的"用位运算榨取信息"。

③ 扩容结束：恢复成正数阈值

sizeCtl = newCap * 0.75;   // 回到"阈值"语义

面试话术："sizeCtl 是一个多态变量：0 未初始化，-1 初始化中，负数表示扩容中且绝对值减一等于参与线程数，正数是扩容阈值。"

05 / TRANSFER

协作扩容：多线程一起搬

HashMap 扩容是"一个线程搬全部"，CHM 是"谁发现需要扩容，谁就帮忙搬一段"。这让扩容的停顿从 O(n) 摊薄到 O(n/线程数)。

① 第一个线程开始迁移，把桶的步长切成段

private static final int MIN_TRANSFER_STRIDE = 16;   // 每个线程至少搬 16 个桶
stride = (NCPU > 1) ? (n >>> 3) / NCPU : n;         // 按核数分片

06 / COUNT

size 统计：为什么不是简单的 ++

CHM 的 size() 不保证精确（并发下本来就是模糊的），但它必须快且不冲突。做法是抄了 LongAdder 的作业。

// baseCount + CounterCell[] 分段累加
private transient volatile long baseCount;
private transient volatile CounterCell[] counterCells;

final long sumCount() {
    CounterCell[] as = counterCells; CounterCell a;
    long sum = baseCount;
    if (as != null) {
        for (int i = 0; i < as.length; ++i) {
            if ((a = as[i]) != null) sum += a.value;
        }
    }
    return sum;
}

为什么不直接 size++

因为 size++ 要 CAS 一个共享变量。高并发下所有线程抢同一个缓存行，CAS 失败重试风暴会让性能急剧下降（伪共享 + 自旋）。

CounterCell 的思路：每个线程在自己的 cell 上累加，读的时候把所有 cell 加起来。写操作几乎无竞争，读操作稍微慢一点——典型的"分散热点"。

size() 到底准不准

不保证。并发插入时 size() 可能略小于真实值（有的累加还没完成）。
所以不要把 size() 当"精确计数"用于业务判断，比如 if (map.size() == 0) 做某事——这个判断在并发下不可靠。
需要精确计数用 mappingCount()（返回 long，不会溢出 int）。

迭代器：弱一致性

CHM 的迭代器不会抛 ConcurrentModificationException，因为它是"弱一致"的：

  • 遍历的是创建那一刻的表结构，期间被删的元素可能还会被遍历到
  • 期间新增的元素可能看不到
  • 但绝不会因为"并发修改"而崩溃

这就是 fail-safe 与 fail-fast 的本质区别：fail-fast 宁可炸掉也不给错数据，fail-safe 保证不炸但允许数据是某一时刻的快照。

07 / COW

CopyOnWriteArrayList：写时复制

思路完全不同：读不加锁，写的时候复制整个数组。适合"读极多、写极少、数据量小"的场景。

public boolean add(E e) {
    synchronized (lock) {                    // 写操作串行
        Object[] es = getArray();
        int len = es.length;
        Object[] newEs = Arrays.copyOf(es, len + 1);   // ★ 复制整个数组
        newEs[len] = e;
        setArray(newEs);                       // volatile 替换引用
        return true;
    }
}

public E get(int index) {
    return elementAt(getArray(), index);       // 读完全无锁
}

① 初始：三个读者共享一个数组

array[A][B][C]
←
读者1
读者2 读者3

② 写者来了：复制一份新数组

旧数组[A][B][C]
→
新数组[A][B][C][D]

复制期间，读者一直读旧数组——完全不阻塞。

③ 替换引用，读者立刻看到新数据

setArray(newEs);   // volatile 写，保证可见性

旧数组交给 GC。之后的新读者读新数组，之前的读者可能还在读旧数组——弱一致。

④ 代价

读写内存
ArrayListO(1)O(1) 均摊小
COWO(1) 无锁O(n) 复制写时翻倍

什么时候该用

白名单、配置列表、监听器列表——读多写少、数据量小（几百个元素以内）。
不要用它做高频写、大数据量的场景，每次 add 都复制整个数组，10 万个元素写一次就是 10 万次拷贝。

任务 2：线程安全缓存 + 三方对比

把今天的知识落成一个真实的缓存实现，再压测对比三种方案。

// 推荐写法：CHM + computeIfAbsent
public class LocalCache<K, V> {
    private final ConcurrentHashMap<K, V> map = new ConcurrentHashMap<>();

    public V get(K key, Function<K, V> loader) {
        return map.computeIfAbsent(key, loader);   // 整个"查-没有就加载-放入"是原子的
    }
}

computeIfAbsent 的两个坑

① 不要在里做耗时操作它会锁住那个桶，loader 慢了会阻塞同桶的其他 key
② 不要在里再操作同一个 map可能死锁或抛 IllegalStateException（递归更新）
方案读写并发度适用
synchronizedMap加锁加锁1几乎不用
Hashtable加锁加锁1遗留代码
ConcurrentHashMap无锁CAS / 桶锁≈ 桶数通用首选
CopyOnWriteArrayList无锁复制全数组写串行读多写少、小数据

压测该看什么

任务要求"比较吞吐"，重点不是绝对数字，而是趋势：

  • 线程数从 1 → 16，CHM 的吞吐应该接近线性增长，synchronizedMap 基本平的
  • COW 在读多写少时吞吐最高，但一旦写比例上来会断崖式下跌
  • 写比例 0%、读 100% 时，COW 甚至可能超过 CHM

09 / SELF CHECK

今天的自测

JDK 7 和 JDK 8 的 CHM 有什么本质区别？

JDK 7 用 Segment 分段锁（继承 ReentrantLock），并发度固定为段数；JDK 8 改为 Node 数组 + CAS（空桶）+ synchronized（非空桶首节点），并发度约等于桶数，且大量操作无需加锁。

JDK 8 CHM 的 put 有哪几条分支？

① table 为空 → initTable（CAS 抢 -1）；② 目标桶为空 → casTabAt 无锁插入；③ 桶首节点是 MOVED（ForwardingNode）→ helpTransfer 帮忙扩容；④ 否则 synchronized 锁住首节点，遍历链表/红黑树插入或覆盖；⑤ 最后 addCount 计数并可能触发扩容。

sizeCtl 的几种取值分别代表什么？

0：未初始化；-1：正在初始化；<-1：正在扩容，绝对值减一等于参与迁移的线程数；正数：扩容阈值。

为什么 CHM 的 key 和 value 都不允许 null？

因为 get 返回 null 无法区分"key 不存在"和"value 就是 null"。并发下无法用 containsKey 二次确认（中间状态可能变化），所以直接禁止，从设计上消除二义性。

协作扩容是怎么实现的？

按 CPU 核数把桶切成 stride 段，多线程各自迁移自己的区间。迁完的桶放入 ForwardingNode（hash = MOVED），其他线程遇到就调 helpTransfer 加入；读操作遇到 ForwardingNode 则转到 nextTable 继续查，因此不会被扩容阻塞。

CHM 的 size 为什么不用简单的 AtomicInteger？

所有线程 CAS 同一个变量会形成热点和自旋风暴。改用 baseCount + CounterCell[] 分散累加，读时求和，思路来自 LongAdder。代价是 size() 在并发下不精确。

CHM 的迭代器为什么不会抛 CME？

它是弱一致迭代器：遍历期间不校验 modCount，允许看到旧值或看不到新值，但保证不崩溃。对比 ArrayList 的 fail-fast 会立即抛异常。

CopyOnWriteArrayList 的原理和适用场景？

写时加锁复制整个数组，然后 volatile 替换引用；读操作完全无锁。适合读多写少、数据量小的场景（白名单、监听器列表）。不适合高频写或大数据量。

CHM 和 synchronizedMap 的性能差异从哪来？

synchronizedMap 所有方法共用一把锁，并发度 1；CHM 读无锁、写只锁单个桶（空桶用 CAS）。线程数增加时 CHM 吞吐近似线性增长，synchronizedMap 基本不变。

computeIfAbsent 有哪些坑？

① loader 里做耗时操作会长时间锁住该桶，阻塞同桶的其他 key；② 在 loader 里再次操作同一个 map 可能死锁或抛异常；③ 返回 null 时不会写入 map（要确认语义）。
