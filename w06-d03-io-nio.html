01 / MATRIX

四象限：别再混着说

BIO / NIO / AIO 这三个词经常被混用。准确的说法是两个维度的组合：谁在等（阻塞与否）、谁在通知（同步还是异步）。

① 两个维度先分清

阻塞 / 非阻塞

说的是调用方：发起 IO 后，线程要不要在那儿干等。

同步 / 异步

说的是数据搬运：谁把数据从内核拷到用户缓冲区。

关键：非阻塞 ≠ 异步。NIO 是非阻塞 + 同步（数据拷贝还得你自己做）。

② 四个格子

同步 + 阻塞 = BIO
线程发起 read 后卡住，直到数据到达并拷完。
一连接一线程。
同步 + 非阻塞 = NIO
read 立即返回（可能没数据），靠 Selector 轮询就绪事件，再由线程去拷贝。
一线程管多连接。
异步 + 阻塞
逻辑上不存在（异步的意义就是不等）。
异步 + 非阻塞 = AIO
发起 read 就返回，内核拷完数据后回调你。
Java 7 引入，实际用得少。

③ 用"去餐厅吃饭"记住

BIO点完菜站在出菜口等，菜好了自己端——你一直站着（阻塞），菜要自己端（同步）
NIO点完菜回座位刷手机，服务员喊"好了"你再去端——不用一直等（非阻塞），但还是自己端（同步）
AIO点完菜回座位，服务员直接把菜送到桌上——不用等，也不用自己端（异步）
0 / 3

最容易被扣分的说法

❌ "NIO 就是非阻塞 IO" —— 不全对，NIO 的 N 官方解释是 New IO（后来也叫 Non-blocking IO），它的核心贡献是 Selector 多路复用，而不只是"非阻塞"。
❌ "AIO 比 NIO 快" —— 不一定。AIO 只是编程模型不同，Linux 上真正的异步 IO（io_uring）普及很晚，Java AIO 在 Linux 上长期是用 epoll 模拟的。

02 / BIO

BIO 的问题：C10K

BIO 的模型是"一个连接一个线程"。连接数一上来，线程就爆了——这是所有高并发服务器的历史起点。

// 最朴素的 BIO 服务器
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept();          // 阻塞：没连接就一直等
    new Thread(() -> {
        InputStream in = socket.getInputStream();
        byte[] buf = new byte[1024];
        while ((len = in.read(buf)) != -1) {   // 阻塞：没数据就一直等
            // 处理
        }
    }).start();
}

为什么撑不住 1 万个连接

线程开销每个线程默认栈 1MB，1 万线程 = 10GB 虚拟内存（虽然可调，但仍很重）
上下文切换线程一多，CPU 大量时间花在切换而不是干活
绝大多数线程在空等1 万个连接里可能只有几十个活跃，其余全卡在 read 上
线程池也救不了池子里的线程被长时间阻塞占用，新连接排队

但 BIO 也有它的位置

连接数少（几十）、逻辑简单、追求开发效率时，BIO + 线程池完全够用。Tomcat 的 BIO 连接器曾经就是默认配置，直到连接数上来了才换成 NIO。

03 / NIO

三件套：Buffer / Channel / Selector

记住一句话：Channel 是管道，Buffer 是容器，Selector 是调度台。数据永远是"读进 Buffer、从 Buffer 写出"。

Channel · 双向管道

和 Stream 最大的区别：Channel 是双向的，一个通道既能读也能写；Stream 只能单向。

FileChannel文件，支持 transferTo（零拷贝）
SocketChannelTCP 客户端
ServerSocketChannelTCP 服务端
DatagramChannelUDP

Buffer · 数据容器

本质是一块内存 + 四个指针。所有 NIO 的"坑"几乎都出在指针上。

ByteBuffer最常用，其余是视图
堆内/堆外allocate vs allocateDirect
视图asIntBuffer / asCharBuffer

读写流程（背下来）

// 写：数据 → Buffer → Channel
buffer.put(data);
buffer.flip();            // ★ 切换到读模式
channel.write(buffer);

// 读：Channel → Buffer → 取数据
buffer.clear();           // 清空，准备写
channel.read(buffer);
buffer.flip();
while (buffer.hasRemaining()) process(buffer.get());

忘记 flip() 是最常见的 bug——写完直接读，position 停在末尾，读出来是空的。

⑤ clear() vs compact()

clear()

position = 0
limit = capacity

数据没删，只是指针重置。未读的 D、E 会被覆盖。

compact()

把未读的 D、E 移到开头
position = 2
limit = capacity

未读数据保留，适合"没读完就要接着读"的场景。

选择口诀：读完了要复用 → clear；没读完要续读 → compact。

堆内 vs 堆外

allocate堆内内存，JVM 管理，GC 友好；但做 IO 时要多一次拷贝到堆外
allocateDirect堆外（DirectByteBuffer），IO 直达，省一次拷贝；但分配/释放慢，需要手动管理，容易 OOM（不受堆限制）

实践：只在长生命周期的 IO 缓冲上用 Direct，用完记得让它被回收（或池化）。

05 / SELECTOR

多路复用：一个线程管一万个连接

Selector 的本质是把"等数据"这件事交给操作系统。线程不再逐个连接阻塞，而是问操作系统："哪些连接好了？"

Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.bind(new InetSocketAddress(8080));
server.configureBlocking(false);              // ★ 必须非阻塞
server.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();                          // 阻塞在这里，直到有事件就绪
    Set<SelectionKey> keys = selector.selectedKeys();
    Iterator<SelectionKey> it = keys.iterator();
    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();                            // ★ 必须手动移除，否则下次还会处理
        if (key.isAcceptable())   handleAccept(key);
        else if (key.isReadable()) handleRead(key);
        else if (key.isWritable()) handleWrite(key);
    }
}

四种事件

OP_ACCEPT有新连接进来（服务端）
OP_CONNECT连接建立完成（客户端）
OP_READ有数据可读
OP_WRITE可以写（缓冲区不满）

底层：select / poll / epoll

机制模型复杂度限制
select把 fd 集合拷给内核，内核遍历O(n)最多 1024 个 fd
poll同 select，但用链表O(n)无数量限制
epoll内核维护红黑树 + 就绪链表O(1) 取就绪无限制

epoll 为什么快

select 每次调用都要把整个 fd 集合从用户态拷到内核态，再让内核遍历一遍看谁就绪——连接越多越慢。

epoll 做了两件事：① 用 epoll_ctl 一次性把 fd 注册进内核的红黑树（不用每次拷）；② 数据就绪时内核主动把 fd 挂到就绪链表，epoll_wait 直接取链表，复杂度 O(1)。

Java NIO 在 Linux 上默认就是 epoll（JDK 的 EPollSelectorImpl）。

06 / ZERO COPY

零拷贝：省掉的到底是哪几次拷贝

"零拷贝"不是真的零次拷贝，而是省掉 CPU 参与的那几次。DMA 拷贝还在，但 CPU 不用管。

① 传统 read + write：4 次拷贝、4 次切换

磁盘文件数据
① DMA 拷贝磁盘 → 内核页缓存
② CPU 拷贝内核页缓存 → 用户缓冲区（read 返回）
③ CPU 拷贝用户缓冲区 → socket 缓冲区（write 调用）
④ DMA 拷贝socket 缓冲区 → 网卡

4 次用户态/内核态切换：read 进入、read 返回、write 进入、write 返回。

② mmap + write：3 次拷贝

用 mmap 把内核页缓存映射到用户空间，省掉"内核→用户"那次拷贝，但"用户→socket"还在。

磁盘文件数据
① DMA磁盘 → 页缓存
② 省掉页缓存直接映射给用户（不再拷贝）
③ CPU页缓存 → socket 缓冲区
④ DMAsocket → 网卡

③ sendfile：2 次拷贝、2 次切换（真正的零拷贝）

磁盘文件数据
① DMA磁盘 → 页缓存
② 省掉不再经过用户空间
③ 省掉（gather）只把"描述符"追加到 socket 缓冲区
④ DMA gather网卡直接从页缓存收集数据

整个过程中 CPU 只发指令，不搬数据。这就是"零拷贝"的含义。

④ Java 里怎么用

FileChannel in = new FileInputStream(file).getChannel();
SocketChannel out = ...;

// 底层走 sendfile（Linux）
long sent = in.transferTo(0, in.size(), out);

// 或者用 MappedByteBuffer（mmap）
MappedByteBuffer mb = in.map(FileChannel.MapMode.READ_ONLY, 0, in.size());

三大 MQ（Kafka / RocketMQ / RabbitMQ）、Netty、Tomcat 的静态文件传输，全都靠这个。

面试要说清的三个数字

传统 read+write：4 次拷贝（2 次 DMA + 2 次 CPU）、4 次切换
mmap + write：3 次拷贝、4 次切换
sendfile：2 次拷贝（都是 DMA）、2 次切换

如果只说"零拷贝就是不用拷贝"，会被追问到底。要说"省掉的是 CPU 拷贝和用户态/内核态切换"。

07 / SERIALIZATION

序列化：三种方案怎么选

方案体积性能可读性跨语言典型场景
Java 原生大慢二进制不支持几乎不用（仅本地缓存）
JSON中中好好HTTP API、前后端交互
Protobuf小快差好RPC、内部服务通信

Java 原生序列化的三个坑

serialVersionUID不显式声明时，编译器按类结构生成。改一个字段，UID 就变，反序列化直接抛 InvalidClassException
安全反序列化可以构造任意对象（历史上多个 RCE 漏洞都出在这里），不要反序列化不可信数据
性能要写类元信息，比 JSON 还大，且反射调用多

所以生产上：对外用 JSON，对内用 Protobuf 或自定义二进制，Java 原生序列化基本只在 `Serializable` 这个"标记"意义上被用到（比如放进 session、RPC 框架的兜底）。

08 / PRACTICE

任务 2：NIO 聊天服务器

核心是"一个线程 + 一个 Selector + 一个广播列表"。写完这个，你就理解了 Netty 在做什么。

public class NioChatServer {
    private static final List<SocketChannel> clients = new CopyOnWriteArrayList<>();

    public static void main(String[] args) throws IOException {
        Selector selector = Selector.open();
        ServerSocketChannel server = ServerSocketChannel.open();
        server.bind(new InetSocketAddress(9000));
        server.configureBlocking(false);
        server.register(selector, SelectionKey.OP_ACCEPT);

        ByteBuffer buffer = ByteBuffer.allocate(1024);

        while (true) {
            selector.select();
            Iterator<SelectionKey> it = selector.selectedKeys().iterator();
            while (it.hasNext()) {
                SelectionKey key = it.next();
                it.remove();
                if (key.isAcceptable()) {
                    SocketChannel c = server.accept();
                    c.configureBlocking(false);
                    c.register(selector, SelectionKey.OP_READ);
                    clients.add(c);
                    System.out.println("新用户，当前 " + clients.size() + " 人");
                } else if (key.isReadable()) {
                    SocketChannel c = (SocketChannel) key.channel();
                    buffer.clear();
                    int n = c.read(buffer);
                    if (n == -1) {              // 客户端断开
                        clients.remove(c); c.close(); key.cancel(); continue;
                    }
                    buffer.flip();
                    byte[] data = new byte[buffer.remaining()];
                    buffer.get(data);
                    String msg = new String(data, StandardCharsets.UTF_8);
                    broadcast(msg, c);
                }
            }
        }
    }

    private static void broadcast(String msg, SocketChannel from) throws IOException {
        ByteBuffer out = ByteBuffer.wrap((from == null ? "[系统] " : "[用户] ") + msg + "\n");
        for (SocketChannel c : clients) {
            if (c != from) { out.rewind(); c.write(out); }   // ★ 每次写前 rewind
        }
    }
}

四个必踩的坑

① 忘了 it.remove()同一个事件会被重复处理，直到抛 CancelledKeyException
② 忘了 flip()写进 buffer 后直接读，读到空
③ 写没写完write() 不保证一次写完，返回值可能是 0 或小于剩余量，需要 while + OP_WRITE 处理
④ 半包/粘包TCP 是字节流，一次 read 可能是半个消息或两个半消息。需要"长度前缀"或分隔符来切分

半包粘包怎么解决

三种常见方案：① 定长（每条消息固定长度，简单但浪费）；② 分隔符（如换行，适合文本协议）；③ 长度前缀（前 4 字节是长度，后面是内容，最通用）。

Netty 的 LengthFieldBasedFrameDecoder 和 LineBasedFrameDecoder 就是干这个的。

BIO vs NIO 的实测差异

指标BIO + 线程池NIO + Selector
连接数上限受线程数限制（几百到几千）受 fd 限制（几万到几十万）
空连接成本一个线程（约 1MB 栈）一个 SelectionKey（几十字节）
编程复杂度简单高（半包、状态机）
适合短连接、低并发长连接、高并发

09 / SELF CHECK

今天的自测

BIO、NIO、AIO 分别属于哪个组合？

BIO = 同步阻塞；NIO = 同步非阻塞（多路复用，数据拷贝仍需自己完成）；AIO = 异步非阻塞（内核拷完回调）。注意"非阻塞 ≠ 异步"。

BIO 为什么撑不住高并发？

一连接一线程：线程栈开销大（默认 1MB）、上下文切换频繁、绝大多数线程阻塞在 read 上浪费资源。线程池只能缓解，不能解决长连接占用问题。

flip() 到底做了什么？

把 limit 设为当前 position（数据边界），再把 position 归零。它不复制数据，只改指针，用于从"写模式"切到"读模式"。

clear() 和 compact() 的区别？

clear 把 position 置 0、limit 置 capacity，未读数据会被覆盖；compact 把未读数据移到开头，position 设为剩余长度，未读数据保留。读完复用用 clear，没读完要续读用 compact。

堆内 Buffer 和堆外 Buffer 怎么选？

堆内（allocate）由 JVM 管理、GC 友好，但 IO 时需要额外拷贝；堆外（allocateDirect）IO 直达省一次拷贝，但分配慢、不受堆限制、需要池化或注意回收。长生命周期的 IO 缓冲用堆外更划算。

Selector 的核心作用是什么？

把"等待数据到达"交给操作系统，线程只需调用 select() 等待就绪事件，从而实现一个线程管理成千上万个连接，避免一线程一连接的开销。

select、poll、epoll 的差异？

select 每次调用都要把 fd 集合拷进内核并遍历，O(n) 且有 1024 上限；poll 用链表解除数量限制但仍 O(n)；epoll 用红黑树注册 + 就绪链表，取就绪事件 O(1)，无数量限制。

零拷贝省掉了哪几次拷贝？

传统 read+write 是 4 次拷贝（2 次 DMA + 2 次 CPU）、4 次上下文切换。sendfile 降到 2 次 DMA 拷贝、2 次切换，CPU 完全不参与搬运，所以叫"零拷贝"。mmap 居中，3 次拷贝。

Java 里怎么用零拷贝？

FileChannel.transferTo/transferFrom（底层 sendfile）、FileChannel.map 得到 MappedByteBuffer（mmap）。Kafka、Netty、Tomcat 静态资源都依赖它。

为什么 NIO 会有半包/粘包问题？怎么解决？

TCP 是字节流，没有消息边界：一次 read 可能拿到半个消息，也可能拿到两个半。解决方式：定长、分隔符、长度前缀（最通用）。Netty 用 LengthFieldBasedFrameDecoder 等解码器处理。

Java 原生序列化为什么不用了？

体积大（带类元信息）、性能差（反射）、跨语言不支持，而且反序列化不可信数据有 RCE 风险。对外用 JSON，内部 RPC 用 Protobuf。
