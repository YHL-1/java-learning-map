01 / OVERVIEW

只需要 7 个

23 种是 GoF 的分类，但日常写业务代码真正会用到的就这几个。剩下的大多是框架层面的，理解即可。

模式一句话解决的问题Spring 里的例子
单例全局只有一个实例无状态对象重复创建、需要共享状态所有 Bean 默认单例
工厂把创建逻辑集中调用方不该知道怎么 newBeanFactory / FactoryBean
策略同一行为的不同实现消除 if-else / switchResource、PlatformTransactionManager
模板方法父类定骨架，子类填步骤固定流程 + 可变步骤JdbcTemplate、AbstractApplicationContext
责任链一个个处理，通过则往下多步校验、过滤Filter、HandlerInterceptor
代理不直接访问目标，中间加一层横切逻辑（日志、事务）AOP（W05 D5 已讲）
观察者状态变化通知订阅者解耦"发生了什么"和"要做什么"ApplicationEvent / Listener

判断该不该用模式的标准

不是"这里能用策略模式"，而是"这里不用模式会不会疼"。
三个 if-else 分支，直接写最清楚；十个分支、每个月还在加，就该抽策略了。模式是给变化准备的，不是给简单准备的。

02 / SINGLETON

单例：五种写法，只有一种满分

① 饿汉式：简单但可能浪费

public class Config {
    private static final Config INSTANCE = new Config();
    private Config() {}
    public static Config getInstance() { return INSTANCE; }
}

类加载时就创建。线程安全（JVM 保证），但如果这个对象很重且不一定用得上，就浪费了。

② 懒汉式：有并发 bug

private static Config instance;
public static Config getInstance() {
    if (instance == null) instance = new Config();   // ❌ 多线程下会创建多个
    return instance;
}

加 synchronized 能修好，但每次 getInstance 都要抢锁，性能差。

③ 双重检查锁（DCL）：必须加 volatile

private static volatile Config instance;   // ★ volatile 不能省
public static Config getInstance() {
    if (instance == null) {
        synchronized (Config.class) {
            if (instance == null) instance = new Config();
        }
    }
    return instance;
}

为什么必须 volatile：new 分三步——① 分配内存 ② 初始化对象 ③ 引用指向内存。② 和 ③ 可能被指令重排，导致别的线程拿到尚未初始化完成的对象。volatile 禁止这个重排。

④ 静态内部类：优雅的懒加载

public class Config {
    private Config() {}
    private static class Holder {
        private static final Config INSTANCE = new Config();
    }
    public static Config getInstance() { return Holder.INSTANCE; }
}

利用 JVM 的类初始化机制：Holder 类只在第一次调用 getInstance 时才加载，加载时创建实例，由 JVM 保证线程安全。既懒加载、又无锁、又安全。

⑤ 枚举：唯一能防住反射和反序列化的写法

public enum Config {
    INSTANCE;
    public void load() { ... }
}

《Effective Java》推荐这种。原因：

防反射Constructor.newInstance 遇到枚举会直接抛 IllegalArgumentException
防反序列化枚举反序列化走 valueOf，天然返回同一个实例，不会 new 新的
线程安全JVM 保证枚举实例的创建是线程安全的
缺点不能继承、写法略反直觉、不符合"类"的直觉

03 / FACTORY

工厂：三种，别混

类型结构什么时候用
简单工厂一个方法 + switch 创建不同实现产品少、变化少（严格说不算 GoF 模式）
工厂方法每种产品一个工厂类产品会持续增加，不想改已有代码
抽象工厂一个工厂创建一族产品产品有"系列"概念（如不同主题的 UI 组件）
// 简单工厂：够用就好，别过度设计
public class PayChannelFactory {
    public static PayChannel create(String type) {
        return switch (type) {
            case "alipay" -> new AliPay();
            case "wechat" -> new WeChatPay();
            default -> throw new BizException(ErrorCode.UNSUPPORTED_CHANNEL);
        };
    }
}

简单工厂的问题：加一个渠道就要改这个类

违反开闭原则。但它简单直观，产品稳定时完全够用。
真正要"新增不修改"时，才升级成"策略 + 注册表"（下一节），而 Spring 的 Map<String, PayChannel> 注入就是这个模式的终极形态。

04 / STRATEGY

策略：把 if-else 抽出去

这是业务代码里性价比最高的一个模式。任务要求"用策略 + 工厂重构支付模块"，看下面这段演变。

重构前

public void pay(Order o, String type) {
    if ("alipay".equals(type)) {
        // 30 行支付宝逻辑
    } else if ("wechat".equals(type)) {
        // 30 行微信逻辑
    } else if ("union".equals(type)) {
        // 30 行银联逻辑
    } else {
        throw new BizException("不支持的渠道");
    }
}

重构后

public interface PayChannel {
    String type();
    void pay(Order o);
}

public void pay(Order o, String type) {
    PayChannel c = channels.get(type);
    if (c == null) throw new BizException("不支持的渠道");
    c.pay(o);
}

① 定义接口，每个渠道一个实现类

@Component
public class AliPay implements PayChannel {
    public String type() { return "alipay"; }
    public void pay(Order o) { /* ... */ }
}

② Spring 自动把同类型 Bean 注入成 Map

@Service
public class PayService {
    // key = bean 名字（aliPay / weChatPay），value = 实现
    private final Map<String, PayChannel> channels;

    public PayService(List<PayChannel> list) {
        this.channels = list.stream()
            .collect(Collectors.toMap(PayChannel::type, Function.identity()));
    }
}

新增渠道 = 新增一个类，不用改任何已有代码。@Component 自动被扫到，Map 自动组装。

③ 调用方彻底干净

payService.pay(order, "alipay");   // 没有一行 if-else

这就是"策略 + 工厂 + 依赖注入"三合一的效果，也是 Spring 项目里最常见的重构范式。

什么时候不要用策略

只有两三个分支、且大概率不会再增加时，抽成 3 个类 + 1 个接口反而更难看懂。判断标准：这段 if-else 未来会不会长。

05 / TEMPLATE

模板方法：父类定骨架，子类填步骤

适合"流程固定、个别步骤不同"的场景。JdbcTemplate 就是典型：连接、执行、关闭都由父类管，只有 SQL 和结果映射由你写。

public abstract class AbstractOrderService {

    // ★ final：骨架不允许子类改
    public final Order create(CreateCmd cmd) {
        validate(cmd);              // 固定步骤
        Order order = buildOrder(cmd);  // 抽象方法，子类实现
        beforeSave(order);          // 钩子，默认空实现
        save(order);                // 固定步骤
        afterSave(order);           // 钩子
        return order;
    }

    protected abstract Order buildOrder(CreateCmd cmd);   // 必须实现
    protected void beforeSave(Order o) { }                  // 钩子，可选
    protected void afterSave(Order o) { }
    private void validate(CreateCmd cmd) { ... }              // 私有，子类看不到
    private void save(Order o) { ... }
}

抽象方法 vs 钩子方法

抽象方法子类必须实现，是流程中的关键可变点
钩子方法空实现，子类按需覆盖，用来插入扩展

为什么骨架方法要 final

防止子类重写整个流程，破坏"模板"的约束。
Spring 的 JdbcTemplate.execute()、AbstractApplicationContext.refresh() 都是这个思路。

模板方法 vs 策略

模板方法用继承，父类控流程——适合"步骤顺序固定"。
策略用组合，调用方选实现——适合"整段逻辑可替换"。
现代设计更推荐组合（策略），因为继承耦合太强，但模板方法在框架里仍然大量存在。

06 / CHAIN

责任链：一个接一个，通过则继续

任务要求"用责任链实现订单校验"。它的价值是：每个校验规则独立、可插拔、可排序。

public interface OrderValidator {
    void validate(Order order);   // 不通过就抛异常
}

@Component @Order(1)
public class StockValidator implements OrderValidator {
    public void validate(Order o) {
        if (stock < o.qty()) throw new BizException(ErrorCode.STOCK_NOT_ENOUGH);
    }
}

@Component @Order(2)
public class AmountLimitValidator implements OrderValidator { ... }

// 由 Spring 收集所有实现，按 @Order 排序
@Service
public class OrderService {
    private final List<OrderValidator> validators;
    public OrderService(List<OrderValidator> vs) { this.validators = vs; }

    public void create(Order o) {
        validators.forEach(v -> v.validate(o));   // 链式校验
    }
}

两种责任链实现

链表式每个 handler 持有 next，自己能决定"是否继续"（如 Filter 可以 return 不往下走）
列表式由一个容器按顺序遍历，简单直接（上面这个例子）

Spring 的 Filter / Interceptor 是链表式，因为需要支持"中断"。订单校验用列表式就够了。

07 / PROXY & OBSERVER

代理与观察者：一个拦，一个通知

代理（W05 D5 已详讲）

在目标前后加逻辑，调用方无感知。

静态代理手写，一个类对一个类
JDK 动态只能代理接口
CGLIB生成子类，不能 final

Spring AOP、MyBatis Mapper、RPC 存根都是它。

观察者

发布事件，多个监听者各自处理，互不耦合。

// 发布
publisher.publishEvent(new OrderCreatedEvent(order));

// 订阅
@EventListener
public void onCreated(OrderCreatedEvent e) {
    // 发短信、加积分、发 MQ ...
}

新增"下单后做什么"，只要加一个 Listener，订单服务不用改。

观察者的两个坑

① 默认同步执行Listener 抛异常会影响主流程，慢会拖慢下单。需要异步要加 @Async + 线程池
② 事务边界在事务提交前收到事件，此时数据可能还没提交，别的线程读不到。要用 @TransactionalEventListener(phase = AFTER_COMMIT)

08 / SPRING

Spring 里对应的 5 个

面试问"你熟悉哪些设计模式"，最高分的答法是：说出模式 + 说出 Spring 里哪个类用了它 + 说清为什么这么设计。

模式Spring 中的实现为什么这么设计
单例Bean 默认 singleton 作用域无状态 Bean 复用，省去反复创建；容器用三级缓存管理生命周期
工厂BeanFactory / FactoryBean把"创建对象"的复杂性（依赖注入、代理包装）从调用方剥离
模板方法JdbcTemplate、AbstractApplicationContext.refresh()固定"拿连接-执行-关闭"骨架，只把 SQL 和映射留给用户
策略PlatformTransactionManager、Resource同一接口不同实现（JDBC / JTA / 本地），运行时切换
代理AOP 的 JDK / CGLIB 代理横切逻辑（事务、日志）与业务解耦，业务代码不用感知
观察者ApplicationEvent + @EventListener把"下单成功"和"发短信/加积分"解耦
责任链Filter、HandlerInterceptor请求依次经过多个处理器，任一环节可以中断

一个能直接用的回答模板

"我最常用的是策略模式。比如支付模块，原来是一个几十行的 if-else，每加一个渠道都要改。后来抽成 PayChannel 接口，每个渠道一个 @Component 实现，用构造器注入 List<PayChannel> 转成 Map。这样新增渠道只要加类，不用改已有代码——这就是开闭原则。Spring 里 PlatformTransactionManager 也是同样的思路。"

09 / SELF CHECK

今天的自测

为什么 DCL 单例必须加 volatile？

因为 new 由"分配内存 → 初始化 → 引用赋值"三步组成，后两步可能被指令重排。别的线程可能看到"引用已非空但对象未初始化完"的中间状态。volatile 禁止这个重排。

静态内部类单例为什么线程安全？

利用 JVM 类初始化机制：Holder 类只在首次调用 getInstance 时被加载，类初始化由 JVM 保证同步（<clinit> 只会执行一次）。所以既懒加载又无锁。

枚举单例为什么能防反射和反序列化？

反射：Constructor.newInstance 对枚举类型直接抛异常；反序列化：枚举走 valueOf 而不是 new，天然返回同一个实例。

简单工厂、工厂方法、抽象工厂的区别？

简单工厂用一个方法根据参数创建产品（不是 GoF 模式）；工厂方法为每种产品定义独立工厂类，新增产品不改已有代码；抽象工厂创建一族相关产品（如不同主题的整套组件）。

策略模式和 if-else 相比，好处在哪？

① 符合开闭原则，新增分支不改已有代码；② 每个策略独立可测；③ 分支逻辑不再挤在一个方法里。代价是类变多，所以分支少且稳定时不必强上。

Spring 怎么把多个实现注入成 Map？

构造器注入 Map<String, PayChannel> 时，key 是 Bean 名字；注入 List<PayChannel> 时按 @Order 排序。也可以自己用 List 转 Map，key 用业务标识（如 type() 返回值）更稳妥。

模板方法中"抽象方法"和"钩子方法"的区别？

抽象方法必须由子类实现，是流程中的必需可变点；钩子方法是空实现，子类按需覆盖，用于插入可选的扩展。模板骨架方法通常声明为 final 防止被整体重写。

责任链有哪些实现方式？

链表式（每个 handler 持有 next，可决定是否继续，如 Filter）和列表式（容器遍历，简单直接）。需要"中断"能力用链表式，纯校验用列表式即可。

@EventListener 有哪两个坑？

① 默认同步执行，Listener 慢或抛异常会拖累主流程，需要 @Async 配线程池；② 在事务提交前触发，此时数据未提交，别的线程读不到，需要用 @TransactionalEventListener(phase = AFTER_COMMIT)。

能说出 Spring 里 5 个设计模式的对应类吗？

单例-Bean 作用域；工厂-BeanFactory/FactoryBean；模板方法-JdbcTemplate/AbstractApplicationContext.refresh()；策略-PlatformTransactionManager；代理-AOP 的 JDK/CGLIB；观察者-ApplicationEvent；责任链-Filter/HandlerInterceptor。
