三个模式，三个落点

责任链validator/：每个校验规则一个类，按 @Order 排序执行
策略pay/：每个支付渠道一个实现，用 Map 注册表分发
单例InMemoryOrderRepo：全局唯一的数据存储（Spring 下就是默认 singleton Bean）

一个容易做错的设计

不要把校验逻辑写进 OrderService.create() 里，那样又变回一坨 if-else。
正确的做法：Service 只负责"编排"——调校验链、算金额、存库、发事件；具体规则全部在 validator 里。

03 / CODE

核心代码：编排 + 校验链 + 策略

@Service
public class OrderService {
    private final OrderRepository repo;
    private final List<OrderValidator> validators;   // 责任链
    private final Map<String, PayChannel> channels;     // 策略表

    public OrderService(OrderRepository repo,
                         List<OrderValidator> validators,
                         List<PayChannel> channels) {
        this.repo = repo;
        this.validators = validators;
        this.channels = channels.stream()
            .collect(Collectors.toMap(PayChannel::type, Function.identity()));
    }

    public Order create(CreateCmd cmd) {
        // 1. 校验（责任链）：任一不通过就抛异常，中断后续
        validators.forEach(v -> v.validate(cmd));

        // 2. 构建领域对象
        Order order = Order.create(cmd.userId());
        cmd.items().forEach(order::addItem);

        // 3. 落库
        repo.save(order);
        log.info("订单创建成功 id={} amount={}", order.id(), order.total());
        return order;
    }

    public void pay(String orderId, String channelType) {
        Order order = repo.findById(orderId)
            .orElseThrow(() -> new BizException(ErrorCode.ORDER_NOT_FOUND));

        PayChannel channel = channels.get(channelType);
        if (channel == null) throw new BizException(ErrorCode.UNSUPPORTED_CHANNEL);

        channel.pay(order);        // 多态：不同渠道不同实现
        order.markPaid();
        repo.save(order);
    }

    public void cancel(String orderId) {
        Order order = repo.findById(orderId)
            .orElseThrow(() -> new BizException(ErrorCode.ORDER_NOT_FOUND));
        if (order.status() == OrderStatus.PAID)
            throw new BizException(ErrorCode.ORDER_CANNOT_CANCEL);
        order.markCancelled();
        repo.save(order);
    }
}

一个校验器长什么样

@Component
@Order(10)                        // 数字越小越先执行
public class StockValidator implements OrderValidator {
    private final StockService stock;

    public void validate(CreateCmd cmd) {
        for (Item it : cmd.items()) {
            int left = stock.available(it.sku());
            if (left < it.qty())
                throw new BizException(ErrorCode.STOCK_NOT_ENOUGH,
                        "SKU " + it.sku() + " 剩余 " + left);
        }
    }
}

这样写的好处（面试可以讲）

  • 新增校验规则 → 只加一个类，不改 OrderService
  • 每条规则可单测，不需要构造整个服务
  • 执行顺序由 @Order 声明，一眼能看出"先校验什么"

04 / WORD COUNT

词频统计：三种写法

这是 D1/D2 的直接应用。重点不是"能不能跑"，而是能不能说出为什么选这个。

① 最朴素：HashMap 计数

Map<String, Integer> map = new HashMap<>();
for (String w : words) {
    map.merge(w, 1, Integer::sum);   // 或 computeIfAbsent + ++
}

merge 比 get + null 判断 + put 少一次查表，且语义清晰。

② 容量预估：省掉全部扩容

int expected = estimateDistinctWords(totalWords);
Map<String, Integer> map =
        new HashMap<>((int) (expected / 0.75f) + 1);

这是 D1 的 JMH 实验结论的直接应用。文本越大，收益越明显。

③ 并发版本：CHM + 原子累加

ConcurrentHashMap<String, LongAdder> map = new ConcurrentHashMap<>();
map.computeIfAbsent(w, k -> new LongAdder()).increment();

// 为什么用 LongAdder 而不是 AtomicLong：
// 单词计数是高频写热点，LongAdder 分段累加，冲突少得多

多线程读同一文件时，按行分片并行处理，最后合并。

④ Top-N：小顶堆（D3 讲过）

PriorityQueue<Map.Entry<String, LongAdder>> heap =
    new PriorityQueue<>(N, Comparator.comparingLong(e -> e.getValue().sum()));

for (var e : map.entrySet()) {
    heap.offer(e);
    if (heap.size() > N) heap.poll();
}

完整链路：NIO 读文件 → 分词 → HashMap/CHM 计数 → 小顶堆 Top-N。

0 / 4

并行版本不一定更快

如果瓶颈在磁盘 IO（读文件），多线程分词帮不上忙，反而多一层合并开销。
正确的测法：先用单线程跑一遍计时，确认时间花在 CPU（分词）还是 IO 上，再决定要不要并行。这个"先测量再优化"的思路，比代码本身更值钱。

05 / ACCEPTANCE

验收清单

✓可运行：一条命令启动，不需要改代码
✓校验完整：库存不足、金额超限、订单不存在、状态非法，全部抛业务异常
✓支付可扩展：新增渠道只需加实现类，OrderService 不改
✓金额正确：全程 BigDecimal，scale=2，compareTo 比较
✓并发安全：仓储用 ConcurrentHashMap，不出现计数错乱
✓有单测：至少 5 个——下单成功、库存不足、重复支付、取消已支付、金额计算
✓词频统计：能跑 100MB 文本，输出 Top-10 且耗时可解释
